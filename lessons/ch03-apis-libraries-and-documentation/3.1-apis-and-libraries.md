# APIs and Libraries

## Libraries and APIs

A **library** is a collection of code someone else already wrote, that you can reuse instead of writing it yourself. WPILib — the library every FRC robot depends on — is exactly this: motor control, sensors, the whole command-based framework, all written once and reused by thousands of teams.

The **API** (Application Programming Interface) is the instructions for how to actually use a library: what classes it gives you, what each one can do, and what you need to pass in. You don't need to know how a library's code works internally — you just need its API. WPILib publishes its API as web pages you can look things up in; Lesson 3.2 shows how to read one.

## Classes, Attributes, and Behaviors

A **class** is the building block a library gives you — it defines a new kind of value, the same way `int` or `double` do, except you (or a library author) define what it means. An **object** is one specific thing built from a class.

Every class bundles two things together:

- **Attributes** — the data it holds. Stored in variables.
- **Behaviors** — what it can do. Defined as methods.

```java
// statusLight is an object, built from WPILib's DigitalOutput class
DigitalOutput statusLight = new DigitalOutput(0);

// a behavior — call a method with the dot operator
statusLight.set(true);
```

`DigitalOutput` is a real WPILib class: it switches one of the robot controller's digital output pins on or off — here pin `0`, wired to a status light. `new` builds the object (Lesson 4.5 covers exactly how); for now, read that line as "make one `DigitalOutput` for pin 0 and call it `statusLight`." A real file also needs an `import` line before it can use `DigitalOutput` — that's Lesson 3.3.

The `.` (dot operator) is how you reach an object's behaviors and attributes. `statusLight.set(true)` means: find the `set` method defined in the `DigitalOutput` class, and run it on this specific object — turning its pin on.

## Why This Matters

You don't need to know how `DigitalOutput` is implemented internally — the calls into the robot controller's hardware, the voltage on the pin, none of it — to use `statusLight.set(true)` correctly. That's the entire point of a library: someone else solved the hard problem once, documented how to use their solution, and you build on top of it instead of starting from scratch.

## Common Pitfalls

- **Confusing a class with an object.** `DigitalOutput` is the class (the blueprint); `statusLight` is one specific object built from it. A robot might have several `DigitalOutput` objects — one per pin.
- **Forgetting the dot operator.** `statusLight set(true)` isn't valid — the dot is what connects an object to its behavior.

## Key Takeaways

- A library is reusable code written by someone else; its API documents how to use it.
- A class defines a new kind of value, bundling attributes (data) and behaviors (methods) together.
- An object is one specific instance built from a class.
- The dot operator (`.`) accesses an object's attributes and behaviors.
