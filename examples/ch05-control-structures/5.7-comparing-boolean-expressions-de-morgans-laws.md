# Comparing Boolean Expressions (De Morgan's Laws) — Worked Example

**Outline ref:** 5.7 — Comparing Boolean Expressions (De Morgan's Laws) (CSA 2.6)
**Pairs with:** [`lessons/ch05-control-structures/5.7-comparing-boolean-expressions-de-morgans-laws.md`](../../lessons/ch05-control-structures/5.7-comparing-boolean-expressions-de-morgans-laws.md)
**Status:** new — authored worked example (fully solved, walked step by step — not a problem to attempt)

## Problem

Autonomous should abort if it is **not** the case that both the gyro is calibrated **and** the drivetrain is enabled. Simplify that negated condition with De Morgan's Law, and check it against a starting `elevatorHeight`/`armAngle` safety condition written the same negated way.

## Step 1: Write the Condition Literally, As Stated

The problem describes "abort if NOT (both are true)" — that translates directly to a negated `&&`:

```java
boolean gyroCalibrated = true;
boolean drivetrainEnabled = false;

if (!(gyroCalibrated && drivetrainEnabled))
{
    abortAutonomous();
}
```

This is correct, but it reads awkwardly — "not true that both" is a double negative to parse in your head every time.

## Step 2: Apply De Morgan's Law

Negating a compound `&&` condition flips it to `||`, and negates each individual part: `!(a && b)` is equivalent to `!a || !b`. Substituting:

```java
if (!gyroCalibrated || !drivetrainEnabled)
{
    abortAutonomous();
}
```

Both versions evaluate identically for every possible combination of the two booleans — but this one reads directly as "either one isn't ready," which is the actual intent.

## Step 3: Confirm It Trace-by-Trace

| `gyroCalibrated` | `drivetrainEnabled` | `!(gyroCalibrated && drivetrainEnabled)` | `!gyroCalibrated \|\| !drivetrainEnabled` |
|---|---|---|---|
| true | true | false | false |
| true | false | true | true |
| false | true | true | true |
| false | false | true | true |

All four rows match — the two forms really are the same condition.

## Step 4: The Same Idea on Relational Operators

Negating a comparison flips its sign, not just its truth value. Consider a safety check that should trip unless the elevator is high enough *and* the arm is angled far enough back:

```java
boolean unsafe = !(elevatorHeight >= 20.0 && armAngle > 45.0);
```

Distributing the `!` flips `&&` to `||`, and flips each comparison's sign (`>=` becomes `<`, `>` becomes `<=`):

```java
boolean unsafe = (elevatorHeight < 20.0 || armAngle <= 45.0);
```

A common mistake here is only adding the `!` without flipping the sign — `!(elevatorHeight >= 20.0)` is `elevatorHeight < 20.0`, **not** `elevatorHeight <= 20.0`. The equal case has to move to the other side.

## Step 5: A Reminder on Object Equality

If `elevatorHeight` or `armAngle` were ever compared against `null` instead of a number (say, checking whether a sensor reading was ever received), `==`/`!=` is the right tool for that — but comparing whether two non-null objects' *contents* match calls for `.equals()` instead, not `==`. That gets its full treatment once Strings arrive in Ch.6; the short version for now is: `==`/`!=` for `null` checks, `.equals()` for content.

## Recap

- `!(a && b)` is equivalent to `!a || !b`; `!(a || b)` is equivalent to `!a && !b`.
- Negating a relational operator flips its sign: `<` becomes `>=`, `>` becomes `<=`, `==` becomes `!=`.
- Simplifying a negated condition often makes its intent easier to read, even though it's logically equivalent either way.
- `==` on objects checks identity, not content — `.equals()` (covered fully in Ch.6) is for comparing what's actually inside.
