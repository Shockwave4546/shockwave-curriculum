# Access, final, and Immutability — Worked Example

## Problem

Write a `MatchLog` for one match. It has a match number, set once when the log is created and never changed afterward, and a list of scoring events recorded as the match happens. Other code needs to read those events for the dashboard — but must never be able to change `MatchLog`'s own data just by editing whatever it gets back.

## Step 1: Plan It First

1. Declare `matchNumber` as a blank `final` field, assigned in the constructor.
2. Declare `events` as a `private final ArrayList<String>`, so it can never be pointed at a different list.
3. Write `record(...)`, which only ever adds to `events`, never reassigns it.
4. Write `getEvents()` to return a defensive copy, not the real list.
5. In `main`, show that copy really is safe to hand out.

## Step 2: The Blank Final Match Number

```java
private final int matchNumber;

public MatchLog(int matchNumber)
{
    this.matchNumber = matchNumber;
}
```

`matchNumber` has no initializer in its declaration — that's legal, because the constructor assigns it exactly once, on the one path through this constructor (the blank final rule). Leaving it unassigned here would be a compile error: `variable matchNumber might not have been initialized`.

## Step 3: Recording Events

```java
private final ArrayList<String> events = new ArrayList<String>();

public void record(String event)
{
    events.add(event);
}
```

`events` is `final` too — it can never be pointed at a different list — but `add(...)` only changes what's *inside* the list, so this still compiles.

## Step 4: Returning Events Without Leaking Them

```java
public List<String> getEvents()
{
    return List.copyOf(events);
}
```

Compare that with the leaky version this worked example is deliberately avoiding: `public ArrayList<String> getEvents() { return events; }` hands back the exact list `MatchLog` uses internally — anything the caller does to it (`.clear()`, `.add(...)`) changes `MatchLog`'s real data, with none of `MatchLog`'s own methods ever running. `List.copyOf(events)` instead gives the caller an unmodifiable snapshot.

## Step 5: The Whole Program

To run this as one file, both classes go in `MatchLogCheck.java`. Java allows only one `public` class per file — the one whose name matches the file — so `MatchLog` is written without `public`. The class holding `main` goes first: on Java 17, running a file with `java MatchLogCheck.java` starts the *first* class in the file, so `main` must live there. Java 25 is more forgiving (it also finds the class named after the file), but main-class-first works on both, so every multi-class program in this course uses it.

```java
import java.util.ArrayList;
import java.util.List;

public class MatchLogCheck
{
    public static void main(String[] args)
    {
        MatchLog log = new MatchLog(42);
        log.record("Auto: scored 2 notes");
        log.record("Teleop: climbed");

        List<String> events = log.getEvents();
        System.out.println("Match " + log.getMatchNumber() + ": " + events);

        try
        {
            events.add("Hacked entry");
        }
        catch (UnsupportedOperationException e)
        {
            System.out.println("getEvents() is safe: " + e.getClass().getSimpleName());
        }
    }
}

class MatchLog
{
    private final int matchNumber;
    private final ArrayList<String> events = new ArrayList<String>();

    public MatchLog(int matchNumber)
    {
        this.matchNumber = matchNumber;
    }

    public void record(String event)
    {
        events.add(event);
    }

    public List<String> getEvents()
    {
        return List.copyOf(events);
    }

    public int getMatchNumber()
    {
        return matchNumber;
    }
}
```

## What It Prints

```
Match 42: [Auto: scored 2 notes, Teleop: climbed]
getEvents() is safe: UnsupportedOperationException
```

The dashboard's copy of `events` prints the two recorded strings. Trying to add to that copy throws instead of silently succeeding, because `List.copyOf(...)` returns an unmodifiable list — proof that this copy really is separate from `MatchLog`'s own data.

## What the Leaky Version Would Let Happen

If `getEvents()` returned `events` directly instead of a copy:

```java
public ArrayList<String> getEvents()
{
    return events; // leak — hands back the real list
}
```

then `log.getEvents().clear();`, called from *outside* `MatchLog`, would silently wipe out the match's real event list — no exception, no warning, and none of `MatchLog`'s own methods would ever run. `private` never stopped that: `events` was `private` in both versions. Only the defensive copy in `getEvents()` actually prevents it.

## What Breaking Each Rule Would Look Like

Each of these edits fails to compile, and each failure matches one rule from the lesson:

- **Leaving the blank final field unassigned.** Adding a second constructor, `public MatchLog() { }`, gives `variable matchNumber might not have been initialized` — that path never assigns it.
- **Reassigning a final field after construction.** Replacing `record`'s body with `matchNumber = 7; events.add(event);` gives `cannot assign a value to final variable matchNumber`.
- **Reassigning a final reference to a new object.** Replacing `record`'s body with `events = new ArrayList<String>();` gives `cannot assign a value to final variable events`. Adding to the list was fine; pointing `events` at a different list isn't.

## Recap

- `matchNumber` is a blank `final` field: no initializer at its declaration, assigned exactly once, in the constructor — the blank final rule.
- `events` is a `private final ArrayList`, only ever appended to through `record(...)`, never reassigned to a different list.
- `getEvents()` returns `List.copyOf(events)`, a defensive copy, instead of the real list — the caller can read it, but can't mutate `MatchLog`'s actual data or even modify the copy at all.
- `private` alone doesn't stop a mutable field from leaking — only returning a defensive copy (instead of the field itself) does.
