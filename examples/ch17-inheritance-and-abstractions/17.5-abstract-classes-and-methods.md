# Abstract Classes and Methods — Worked Example

## Problem

The robot's LED strip can play several light patterns, like a blinking pattern and a rainbow pattern. Every pattern has a name, and every pattern can be played — but each one plays in its own way, and there's no sensible "plain pattern" that isn't one of the specific kinds. Write a `LightPattern` superclass that holds the shared name, can't be built on its own, and forces every kind of pattern to say how it plays.

## Step 1: Decide What's Shared and What Isn't

- **Shared by every pattern, with the same code:** a `name` field, a constructor that sets it, and a `getName()` getter.
- **Every pattern has it, but each one's code is different:** `play()`.
- **Should never exist on its own:** a plain `LightPattern` object.

The last two points are exactly what `abstract` is for: `play()` becomes an abstract method, which makes `LightPattern` an abstract class.

## Step 2: Write the Abstract Superclass

```java
abstract class LightPattern
{
    private String name;

    public LightPattern(String name)
    {
        this.name = name;
    }

    public String getName()
    {
        return name;
    }

    public abstract void play();
}
```

`abstract` goes in the class declaration and on the method. `play()` has no body — just its signature and a semicolon. Everything else is an ordinary class: a private field, a constructor, and a concrete getter.

## Step 3: Write the Concrete Subclasses

Each subclass passes its name up with `super(...)` (Lesson 17.2) and implements `play()` with its own body, marked `@Override`:

```java
class BlinkPattern extends LightPattern
{
    public BlinkPattern()
    {
        super("Blink");
    }

    @Override
    public void play()
    {
        System.out.println("Blinking orange twice per second");
    }
}

class RainbowPattern extends LightPattern
{
    public RainbowPattern()
    {
        super("Rainbow");
    }

    @Override
    public void play()
    {
        System.out.println("Cycling through the rainbow");
    }
}
```

Neither subclass is `abstract`, so each one must implement `play()` — and each does.

## Step 4: Put It Together

```java
public class LightShow
{
    public static void main(String[] args)
    {
        LightPattern[] patterns = { new BlinkPattern(), new RainbowPattern() };

        for (LightPattern p : patterns)
        {
            System.out.print(p.getName() + ": ");
            p.play();
        }
    }
}

abstract class LightPattern
{
    private String name;

    public LightPattern(String name)
    {
        this.name = name;
    }

    public String getName()
    {
        return name;
    }

    public abstract void play();
}

class BlinkPattern extends LightPattern
{
    public BlinkPattern()
    {
        super("Blink");
    }

    @Override
    public void play()
    {
        System.out.println("Blinking orange twice per second");
    }
}

class RainbowPattern extends LightPattern
{
    public RainbowPattern()
    {
        super("Rainbow");
    }

    @Override
    public void play()
    {
        System.out.println("Cycling through the rainbow");
    }
}
```

As in 17.1, the class holding `main` comes first, and it's the only `public` class in the file. `LightPattern` is abstract, but it still works as the array's type (Lesson 17.3): every element is a concrete subclass object. `System.out.print` (no `ln`) keeps the name and the pattern's line together.

## What It Prints

```
Blink: Blinking orange twice per second
Rainbow: Cycling through the rainbow
```

`getName()` comes from `LightPattern` for both objects; `play()` runs each object's own version.

## What Going Wrong Would Look Like

**Building a plain `LightPattern`.** Adding this line to `main` doesn't compile:

```java
LightPattern plain = new LightPattern("Off");
```

```
error: LightPattern is abstract; cannot be instantiated
```

**Forgetting to implement `play()`.** If `RainbowPattern` left out its `play()` method, the compiler would reject the class:

```
error: RainbowPattern is not abstract and does not override abstract method play() in LightPattern
```

Both mistakes are caught before the program ever runs — that's the point of making `LightPattern` abstract.

## Recap

- Put the code every subclass shares (field, constructor, getter) in the abstract class; declare the behavior that differs as an abstract method with no body.
- A class with an abstract method must itself be declared `abstract`, and can't be instantiated with `new`.
- Each concrete subclass calls `super(...)` for the shared constructor and implements every abstract method with `@Override`.
- The abstract class still works as a variable or array type: `LightPattern[] patterns` holds any concrete subclass.
