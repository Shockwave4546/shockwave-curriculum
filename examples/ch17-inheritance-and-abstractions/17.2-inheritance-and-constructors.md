# Inheritance and Constructors — Worked Example

## Problem

Every motor on the robot needs a PWM `port`. A shooter's flywheel motor is a kind of motor that *also* needs a `targetRpm` — the speed it spins up to. Write a `FlywheelMotor` subclass whose constructor takes both values, sets up the port through the superclass, and sets its own target itself. Print a line from each constructor so you can see the order they run in.

## Step 1: Write the Superclass and Its Constructor

```java
class Motor
{
    private int port;

    public Motor(int port)
    {
        this.port = port;
        System.out.println("Motor constructor: port set to " + port);
    }

    public int getPort()
    {
        return port;
    }
}
```

`port` is `private`, and the only constructor takes an `int`. Both facts matter for the subclass: it can't assign `port` itself, and there's no no-argument `Motor()` for Java to call automatically.

## Step 2: Write the Subclass Constructor with `super(...)`

`FlywheelMotor` doesn't inherit `Motor`'s constructor, so it writes its own. Its first statement hands the port up to `Motor`'s constructor with `super(port)`; after that, it sets its own field:

```java
class FlywheelMotor extends Motor
{
    private double targetRpm;

    public FlywheelMotor(int port, double targetRpm)
    {
        super(port); // runs Motor's constructor, which sets the private port field
        this.targetRpm = targetRpm;
        System.out.println("FlywheelMotor constructor: target set to " + targetRpm);
    }

    public void describe()
    {
        System.out.println("Flywheel on port " + getPort() + ", target " + targetRpm + " RPM");
    }
}
```

`super(port)` doesn't create a separate `Motor` object — it runs `Motor`'s initialization on *this* object, the one being built. `this.targetRpm` is `FlywheelMotor`'s own field, so it assigns that one directly (with `this`, since the parameter has the same name — Ch.8). `describe()` reads the port through the inherited `getPort()`, because the `port` field itself is private to `Motor`.

## Step 3: Build One and Watch the Order

```java
public class FlywheelDemo
{
    public static void main(String[] args)
    {
        FlywheelMotor shooterWheel = new FlywheelMotor(9, 4500.0);
        shooterWheel.describe();
    }
}

class Motor
{
    private int port;

    public Motor(int port)
    {
        this.port = port;
        System.out.println("Motor constructor: port set to " + port);
    }

    public int getPort()
    {
        return port;
    }
}

class FlywheelMotor extends Motor
{
    private double targetRpm;

    public FlywheelMotor(int port, double targetRpm)
    {
        super(port); // runs Motor's constructor, which sets the private port field
        this.targetRpm = targetRpm;
        System.out.println("FlywheelMotor constructor: target set to " + targetRpm);
    }

    public void describe()
    {
        System.out.println("Flywheel on port " + getPort() + ", target " + targetRpm + " RPM");
    }
}
```

As in 17.1, the three classes share one file, only the `main` class is `public`, and it comes first.

## What It Prints

```
Motor constructor: port set to 9
FlywheelMotor constructor: target set to 4500.0
Flywheel on port 9, target 4500.0 RPM
```

`main` only ever says `new FlywheelMotor(...)`, yet `Motor`'s constructor prints first. That's the chain from the lesson: `Object()` runs, then `Motor(int)`, then the rest of `FlywheelMotor`'s own constructor body. By the time `FlywheelMotor` sets `targetRpm`, the inherited `port` is already set up.

## What Going Wrong Would Look Like

**Assigning the private field directly.** Replacing `super(port);` with this doesn't compile:

```java
public FlywheelMotor(int port, double targetRpm)
{
    this.port = port; // error: port has private access in Motor
    this.targetRpm = targetRpm;
}
```

**Leaving out `super(...)` entirely.** This doesn't compile either:

```java
public FlywheelMotor(int port, double targetRpm)
{
    this.targetRpm = targetRpm; // error: Java inserts super() here, but Motor has no Motor()
}
```

With no explicit `super(...)`, Java inserts a no-argument `super()` call — but `Motor`'s only constructor needs an `int`, so there's nothing for that call to match. (The first broken version above has this same problem too, since it also has no `super(...)`. The compiler reports both errors for it.) The fix for both is the same line from Step 2: `super(port);`.

## Recap

- Constructors aren't inherited: `FlywheelMotor` writes its own, and calls `super(port)` to run `Motor`'s constructor on the same object.
- `super(...)` is the only way to initialize the superclass's `private` fields — `this.port = port;` in the subclass doesn't compile.
- With no explicit `super(...)`, Java inserts `super()` — which fails to compile if the superclass has no no-argument constructor, like `Motor`.
- Construction runs top-down: `Object`, then `Motor`, then `FlywheelMotor`'s own code — so inherited fields are ready before the subclass's code uses them.
