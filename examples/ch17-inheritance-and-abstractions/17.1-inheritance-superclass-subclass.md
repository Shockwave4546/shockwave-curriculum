# Inheritance, Superclass, Subclass — Worked Example

## Problem

A robot has several sensors, and every one of them needs the same two things: a label (like `"Elevator Bottom"`) and a way to print a labeled reading to the console. One of those sensors is a limit switch at the bottom of the elevator, which also needs its own shortcut for reporting that it's been pressed. Write the shared sensor code once, and have the limit switch reuse it instead of copying it.

## Step 1: Write the Shared Superclass

Start with everything *every* sensor needs, in one class. This is **generalization** — pulling the shared parts up into one common parent:

```java
class Sensor
{
    private String label;

    public void setLabel(String label)
    {
        this.label = label;
    }

    public String getLabel()
    {
        return label;
    }

    public void report(String reading)
    {
        System.out.println("[" + label + "] " + reading);
    }
}
```

Nothing here is new — it's an ordinary class with one field, a setter, a getter, and one more method (Ch.7). What makes it a *superclass* is only how the next class uses it.

## Step 2: Apply the is-a Test Before Writing `extends`

Before reaching for inheritance, check that the relationship is genuinely is-a: a limit switch *is a* sensor. Substitution test — anywhere the code expects "a sensor" (give it a label, ask it to report a reading), a limit switch would make complete sense. It passes, so `extends` is the right tool.

## Step 3: Write the Subclass with `extends`

```java
class LimitSwitch extends Sensor
{
    public void reportPressed()
    {
        report("pressed");
    }
}
```

`extends Sensor` is the whole inheritance setup. `LimitSwitch` now has `setLabel()`, `getLabel()`, and `report()` without writing any of them again. It adds one method of its own, `reportPressed()` — that's **specialization**: most of the parent's behavior, plus something specific to this kind of sensor. Notice `reportPressed()` doesn't rebuild the `"[" + label + "] "` formatting; it just calls the inherited `report()`.

## Step 4: Put It Together in One File

To run this as one file, all three classes go in `SensorDemo.java`. Java allows only one `public` class per file — the one whose name matches the file — so `Sensor` and `LimitSwitch` are written without `public`. The class holding `main` goes first: on Java 17, running a file with `java SensorDemo.java` starts the *first* class in the file, so `main` must live there. Java 25 is more forgiving (it also finds the class named after the file), but main-class-first works on both, so every multi-class program in this course uses it. (In a real robot project, each class would get its own file, like the lesson's examples.)

```java
public class SensorDemo
{
    public static void main(String[] args)
    {
        LimitSwitch bottomSwitch = new LimitSwitch();
        bottomSwitch.setLabel("Elevator Bottom");

        bottomSwitch.report("online");   // inherited from Sensor
        bottomSwitch.reportPressed();    // LimitSwitch's own method
        System.out.println("Label: " + bottomSwitch.getLabel()); // inherited from Sensor
    }
}

class Sensor
{
    private String label;

    public void setLabel(String label)
    {
        this.label = label;
    }

    public String getLabel()
    {
        return label;
    }

    public void report(String reading)
    {
        System.out.println("[" + label + "] " + reading);
    }
}

class LimitSwitch extends Sensor
{
    public void reportPressed()
    {
        report("pressed");
    }
}
```

`bottomSwitch` is a `LimitSwitch`, yet `main` calls `setLabel()`, `report()`, and `getLabel()` on it — none of which are written inside `LimitSwitch`. They come from `Sensor`, through `extends`.

## What It Prints

```
[Elevator Bottom] online
[Elevator Bottom] pressed
Label: Elevator Bottom
```

The first two lines have identical formatting because both go through the same inherited `report()` method — there's only one copy of that code, in `Sensor`.

## Step 5: Where has-a Fits Instead

The elevator itself *uses* this limit switch. Should `Elevator` extend `LimitSwitch` (or `Sensor`) to get access to it? Run the substitution test: would an elevator make sense anywhere the code expects "a sensor"? No — an elevator isn't a *kind of* sensor; it just *has* one. That's has-a, so it's modeled as a field, not `extends`:

```java
class Elevator
{
    private LimitSwitch bottomSwitch; // has-a: an Elevator holds a LimitSwitch, isn't one
}
```

`Elevator` has no `extends` at all — which, as the lesson notes, means its implicit superclass is `Object`.

## Recap

- `extends` sets up inheritance: `LimitSwitch extends Sensor` gives `LimitSwitch` every method `Sensor` has, without rewriting them.
- Generalization pulled the shared label/report code up into `Sensor`; specialization let `LimitSwitch` add its own `reportPressed()` on top.
- Run the is-a substitution test before writing `extends` — a limit switch passes as "a sensor"; an elevator doesn't.
- When one class just holds and uses another (an `Elevator` holding a `LimitSwitch`), that's has-a — a field, not `extends`.
