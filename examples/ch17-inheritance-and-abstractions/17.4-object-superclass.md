# Object Superclass — Worked Example

## Problem

The pit crew tracks robot batteries by their label, like `"B07"`. The pit log uses a basic `Battery` object, and the match-readiness check uses a `CompetitionBattery`, which also records the battery's resting voltage. Make both print a useful description, with the subclass building on the superclass's description instead of repeating it. Two objects should count as equal when they have the same label, since that means they describe the same physical battery.

## Step 1: Override `toString()` in the Superclass

`Battery` has no `extends`, so its superclass is `Object`, and it inherits `Object`'s `toString()`. That default prints something like `Battery@5ca881b5`, which is no use to the pit crew. Override it:

```java
class Battery
{
    private String label;

    public Battery(String label)
    {
        this.label = label;
    }

    @Override
    public String toString()
    {
        return "Battery " + label;
    }
}
```

`@Override` tells the compiler "this is meant to replace a method I inherited." If the signature were misspelled (say, `tostring()`), the compiler would report an error instead of silently adding a new, unused method.

## Step 2: Build on It in the Subclass with `super.toString()`

`CompetitionBattery` wants the same `"Battery B07"` text plus its voltage. Instead of rebuilding the label text (which it couldn't do anyway, since `label` is private to `Battery`), it calls `super.toString()` and adds to the result:

```java
class CompetitionBattery extends Battery
{
    private double restingVolts;

    public CompetitionBattery(String label, double restingVolts)
    {
        super(label);
        this.restingVolts = restingVolts;
    }

    @Override
    public String toString()
    {
        return super.toString() + " (" + restingVolts + "V at rest)";
    }
}
```

`super.toString()` runs `Battery`'s version, which returns `"Battery B07"`. `CompetitionBattery`'s version then appends the voltage.

## Step 3: Override `equals()` Once, in the Superclass

Without an override, `equals` is `Object`'s version: it only returns `true` for the exact same object, just like `==`. Add the lesson's four-step recipe to `Battery`, comparing labels:

```java
@Override
public boolean equals(Object other)
{
    if (this == other) return true;                // 1. same object
    if (!(other instanceof Battery)) return false; // 2. must be a Battery
    Battery o = (Battery) other;                   // 3. safe to cast now
    return this.label.equals(o.label);             // 4. compare labels
}
```

The parameter is `Object`, matching the method `Object` declares, so this overrides it. The labels are compared with `.equals()`, not `==`, because they're `String`s. `CompetitionBattery` deliberately does *not* get its own `equals`: only one class in the hierarchy should own it. A `CompetitionBattery` passes the `instanceof Battery` check (it *is a* `Battery`), so it inherits this same comparison.

## Step 4: Pair `equals()` with `hashCode()`

`equals` now says two `Battery` objects with the same label are equal, so their hash codes must match too, or a `HashSet<Battery>` of the pit's batteries wouldn't find `B07` again (Lesson 17.4). Build `hashCode()` from the same field `equals` compares:

```java
@Override
public int hashCode()
{
    return label.hashCode(); // same label -> same hash code
}
```

`CompetitionBattery` inherits this too, so every battery labeled `"B07"` returns the same hash code.

## Step 5: Put It Together

```java
public class BatteryDemo
{
    public static void main(String[] args)
    {
        Battery pitLogEntry = new Battery("B07");
        CompetitionBattery matchCheck = new CompetitionBattery("B07", 12.9);

        System.out.println(pitLogEntry);
        System.out.println(matchCheck);

        System.out.println(pitLogEntry == matchCheck);
        System.out.println(pitLogEntry.equals(matchCheck));
        System.out.println(matchCheck.equals(pitLogEntry));
    }
}

class Battery
{
    private String label;

    public Battery(String label)
    {
        this.label = label;
    }

    @Override
    public String toString()
    {
        return "Battery " + label;
    }

    @Override
    public boolean equals(Object other)
    {
        if (this == other) return true;                // 1. same object
        if (!(other instanceof Battery)) return false; // 2. must be a Battery
        Battery o = (Battery) other;                   // 3. safe to cast now
        return this.label.equals(o.label);             // 4. compare labels
    }

    @Override
    public int hashCode()
    {
        return label.hashCode(); // same label -> same hash code
    }
}

class CompetitionBattery extends Battery
{
    private double restingVolts;

    public CompetitionBattery(String label, double restingVolts)
    {
        super(label);
        this.restingVolts = restingVolts;
    }

    @Override
    public String toString()
    {
        return super.toString() + " (" + restingVolts + "V at rest)";
    }
}
```

## What It Prints

```
Battery B07
Battery B07 (12.9V at rest)
false
true
true
```

- Lines 1-2: `println` calls each object's `toString()` automatically (Ch.7). `matchCheck` runs `CompetitionBattery`'s version, which reuses `Battery`'s through `super.toString()`.
- Line 3: `==` is `false`. These are two separate objects, even though they describe the same battery.
- Lines 4-5: `equals` is `true` in *both* directions, which is the symmetry requirement. Both calls run the one `equals` in `Battery`, and both objects pass `instanceof Battery`. If `CompetitionBattery` had its own `equals` checking `instanceof CompetitionBattery`, line 5 would be `false` while line 4 stayed `true`. That's the subclass trap from the lesson.

## Recap

- Every class inherits `toString()`, `equals(Object other)`, and `hashCode()` from `Object`; `Battery` overrides all three.
- A subclass's `toString()` can call `super.toString()` and add to it, as `CompetitionBattery` does.
- The `equals` recipe is: check `this == other`, check `instanceof`, cast, then compare fields. The parameter type is always `Object`.
- Whenever `equals` is overridden, `hashCode()` is too, built from the same field (`label`).
- Only one class in the hierarchy owns `equals`. Here that's `Battery`, which keeps `a.equals(b)` and `b.equals(a)` in agreement.
