# Structuring a Command-Based Robot Project — Worked Example

## Problem

A practice robot has one mechanism: an `Arm`, driven by a motor on PWM channel 9. The team wants:

- Holding the operator's **left bumper** raises the arm at 40% speed; releasing it stops the arm.
- In autonomous, the arm raises for 1.5 seconds, then stops.

Lay out where every piece of this goes in a WPILib 2027 Commands v3 project: the constants, the `Arm` mechanism, `Robot`, a teleop opmode, and an autonomous opmode.

## Step 1: Plan It First

1. Put the tunable numbers (motor channel, raise speed, controller port) in the `constants` package.
2. Give `Arm` an instance factory method for its "raise" command, since that command only involves the arm.
3. Keep `Robot` thin: create the controller and the arm, and run the scheduler.
4. Bind the bumper in a teleop opmode's constructor.
5. Build the timed raise in an autonomous opmode, and schedule it in `start()`.

## Step 2: Constants — Every Tunable Number in One Place

```java
public final class ArmConstants
{
    public static final int MOTOR_CHANNEL = 9; // PWM channel
    public static final double RAISE_SPEED = 0.4;
}
```

```java
public final class DriverConstants
{
    public static final int OPERATOR_CONTROLLER_PORT = 1;
}
```

Both classes live in the `constants` package. If the arm moves to a different PWM channel, or the drive team wants it faster, exactly one line changes, and `final` means no code can accidentally reassign either value while the robot runs.

## Step 3: `Arm` — A Single-Mechanism Command Lives on the Mechanism

```java
public class Arm implements Mechanism
{
    public Command raiseCommand()
    {
        return run(coroutine -> {
            set(ArmConstants.RAISE_SPEED);
            coroutine.park();
        }).whenExited(() -> set(0.0)).named("Raise Arm");
    }
}
```

(`set(double speed)` is the arm's own method for driving its motor on `ArmConstants.MOTOR_CHANNEL`; the hardware setup is left out here.)

`raiseCommand()` only involves the arm, so an instance factory method on `Arm` is the natural home, in the `mechanisms` package. Because it's built with the mechanism's own `run(...)`, the command automatically requires `this` arm. `park()` keeps the arm raising until something cancels the command, and `whenExited(...)` stops the motor however the command ends.

## Step 4: `Robot` — Deliberately Thin

```java
public class Robot extends OpModeRobot
{
    final CommandXboxController operatorController =
        new CommandXboxController(DriverConstants.OPERATOR_CONTROLLER_PORT);
    final Arm arm = new Arm();

    @Override
    public void robotPeriodic()
    {
        Scheduler.getDefault().run();
    }
}
```

`Robot` creates the controller and the arm, and runs the scheduler every loop. Its fields are package-private and `final`, so the opmodes in the same package can read `robot.arm`, but nothing can replace it. Nothing about bumpers or autonomous appears here at all.

## Step 5: The Teleop Opmode — Bindings for One Mode

```java
@Teleop
public class ArmTeleop implements OpMode
{
    public ArmTeleop(Robot robot)
    {
        robot.operatorController.leftBumper().whileTrue(robot.arm.raiseCommand());
    }
}
```

- The framework finds this class by its `@Teleop` annotation and constructs it when the drive team selects it, passing in the `Robot`.
- `whileTrue` raises the arm while the bumper is held, and cancels the command on release — which runs `whenExited(...)` and stops the arm.
- The binding belongs to this opmode's scope: it only works while `ArmTeleop` is the selected opmode.

## Step 6: The Autonomous Opmode — A Timed Raise

```java
@Autonomous(name = "Raise Arm")
public class RaiseArmAuto implements OpMode
{
    private final Command routine;

    public RaiseArmAuto(Robot robot)
    {
        routine = robot.arm.raiseCommand().withTimeout(Seconds.of(1.5));
    }

    @Override
    public void start()
    {
        Scheduler.getDefault().schedule(routine);
    }
}
```

- The autonomous command reuses the same factory, with `withTimeout(Seconds.of(1.5))` giving it an end condition. When the timeout cancels the raise, `whenExited(...)` stops the arm. Each call to `raiseCommand()` builds a brand-new command object, so the teleop binding and autonomous never share one instance.
- The constructor runs when the opmode is *selected*, while the robot is still disabled, so it only builds the routine. `start()` runs once when the robot is enabled — that's when the routine is scheduled.
- Because the routine is scheduled inside the autonomous opmode, the scheduler cancels it automatically if autonomous ends first. There's no teleop code to write for that.

## Recap

- `constants` package: every tunable number, `public static final`, ALL_CAPS, one small class per topic.
- `mechanisms` package: a command that only involves one mechanism is an instance factory method on it.
- `Robot`: package-private `final` mechanisms and controllers, plus `Scheduler.getDefault().run()` in `robotPeriodic()`.
- Opmodes: a teleop opmode makes its bindings in its constructor; an autonomous opmode builds its routine in the constructor and schedules it in `start()`, and scopes cancel it automatically when the mode ends.
