# Commands & Command Compositions — Worked Example

## Problem

A `Feeder` class that `implements Mechanism` has three methods: `spin(double speed)`, `stop()`, and `hasPiece()` (which returns `true` once a game piece is fully loaded). Write a command factory on `Feeder` that spins the feeder at `0.6` until a piece is loaded, and makes sure the feeder stops however the command ends. Then write a short "back the piece off slightly" command — spin at `-0.2` for a tenth of a second — so the piece isn't jammed against the shooter wheels, and compose the two into one command.

## Step 1: Plan It First

1. Sort the behavior into the parts of one command body: what runs once at the start, what repeats every loop, and when it ends.
2. Decide where the "stop the feeder" cleanup goes so it also runs if the command is canceled.
3. Write the feed command with an explicit loop, then shorten it with a coroutine helper.
4. Write the back-off command with a timed pause.
5. Chain them with `andThen(...)` and name the result.

## Step 2: Sort the Behavior Into One Body

| Part | What goes there |
|---|---|
| Before the loop (once, at the start) | `spin(0.6)` |
| The loop (once per scheduler loop) | nothing to do each loop — just `coroutine.yield()` to pause |
| The loop's condition | keep going while `!hasPiece()` |
| Cleanup on *every* exit | `stop()` |

The cleanup can't just go after the loop: if the driver cancels the command before a piece arrives, the body stops at its last `yield()` and never reaches the code after the loop. `whenExited(...)` runs on every exit — finished or canceled — so that's where `stop()` belongs.

## Step 3: Write It With an Explicit Loop

```java
public Command feedUntilLoadedCommand()
{
    return run(coroutine -> {
        spin(0.6);
        while (!hasPiece())
        {
            coroutine.yield();
        }
    }).whenExited(() -> stop()).named("Feed Until Loaded");
}
```

- `run(...)` is the `Mechanism` interface's factory, so the command automatically requires this feeder — no other command can drive the feeder while this one runs.
- The loop body is only `coroutine.yield()`: each loop, the command checks `hasPiece()` and, if there's no piece yet, pauses until the next loop. Without that `yield()`, the loop would spin forever inside one scheduler run and the whole robot would hang.
- When `hasPiece()` becomes true, the loop ends, the body returns, and the command is finished — then `whenExited` stops the motor.
- `.named("Feed Until Loaded")` turns the builder into a finished `Command`.

## Step 4: Shorten It With `waitUntil`

"Yield until a condition is true" is so common that the coroutine has a helper for it:

```java
public Command feedUntilLoadedCommand()
{
    return run(coroutine -> {
        spin(0.6);
        coroutine.waitUntil(this::hasPiece);
    }).whenExited(() -> stop()).named("Feed Until Loaded");
}
```

`coroutine.waitUntil(this::hasPiece)` does exactly what Step 3's loop did — check, yield, check again — so the behavior is identical.

## Step 5: The Back-Off Command

```java
public Command backOffCommand()
{
    return run(coroutine -> {
        spin(-0.2);
        coroutine.wait(Milliseconds.of(100));
    }).whenExited(() -> stop()).named("Back Off");
}
```

`coroutine.wait(...)` takes a `Time`, made here with `Milliseconds.of(100)` — a tenth of a second. The body pauses for that long (a few scheduler loops), then returns, and `whenExited` stops the motor.

## Step 6: Compose Them

```java
Command loadPiece = feeder.feedUntilLoadedCommand()
    .andThen(feeder.backOffCommand())
    .withAutomaticName();
```

- `andThen(...)` makes a sequential composition: the back-off starts only after the feed command finishes. If the piece never arrives, the feed command never finishes, and the back-off never runs — every step of a sequence has to actually finish.
- `andThen(...)` returns a builder, so the sequence needs a name too; `withAutomaticName()` names it after its members, `"Feed Until Loaded -> Back Off"`.
- `loadPiece` is itself just a `Command`, requiring the feeder for its whole duration — so it can be bound to a button, or composed into something bigger, like any other command.

Each call to a factory method builds a brand-new command object, so `feedUntilLoadedCommand()` can still be bound to its own button somewhere else without clashing with the one inside `loadPiece`.

## Recap

- A v3 command is one body: start-up code, a loop that ends in `coroutine.yield()`, and whatever should happen when the loop's condition says stop.
- Cleanup that must happen however the command ends goes in `whenExited(...)`, not after the loop.
- Coroutine helpers like `waitUntil(...)` and `wait(Milliseconds.of(...))` replace hand-written yield loops.
- `run(...)` makes the command require its mechanism automatically, and every command — including a composition like `andThen(...)` — needs `.named(...)` or `.withAutomaticName()`.
