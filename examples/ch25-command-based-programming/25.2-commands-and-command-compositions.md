# Commands & Command Compositions — Worked Example

## Problem

A `FeederSubsystem` has three methods: `spin(double speed)`, `stop()`, and `hasPiece()` (which returns `true` once a game piece is fully loaded). Write a command that spins the feeder at `0.6` until a piece is loaded, then stops it. Write it first as a full `Command` subclass, then again with a built-in factory — and finally, compose it with a short "back the piece off slightly" step so the piece isn't jammed against the shooter wheels.

## Step 1: Plan It First

1. Decide which lifecycle methods the command needs: start the motor once, finish when a piece is loaded, stop the motor when it ends.
2. Write it as a `Command` subclass, declaring the feeder as its requirement.
3. Rewrite it with `Commands.startEnd(...)` plus the `until(...)` decorator.
4. Chain on a short reverse step with `andThen(...)`, limited by `withTimeout(...)`.

## Step 2: Choose the Lifecycle Methods

| Method | Needed? | Why |
|---|---|---|
| `initialize()` | Yes | Start the motor — once, when the command starts |
| `execute()` | No | Nothing needs to change each loop; the motor keeps its last speed |
| `isFinished()` | Yes | Return `true` once `hasPiece()` is `true` |
| `end(boolean interrupted)` | Yes | Stop the motor — whether the piece arrived or the command was interrupted |

Since `execute()` defaults to doing nothing, it's simply left out.

## Step 3: Write It as a `Command` Subclass

```java
public class FeedUntilLoaded extends Command
{
    private final FeederSubsystem feeder;

    public FeedUntilLoaded(FeederSubsystem subsystem)
    {
        feeder = subsystem;
        addRequirements(feeder);
    }

    @Override
    public void initialize() { feeder.spin(0.6); }

    @Override
    public boolean isFinished() { return feeder.hasPiece(); }

    @Override
    public void end(boolean interrupted) { feeder.stop(); }
}
```

- The feeder is passed in through the constructor (dependency injection), then declared with `addRequirements(feeder)` so no other command can drive the feeder while this one runs.
- `end(...)` ignores `interrupted` here on purpose: whether the piece arrived (`interrupted` is `false`) or the driver canceled it early (`interrupted` is `true`), the right cleanup is the same — stop the motor.

## Step 4: Rewrite It With a Factory

This command has no internal state of its own — it only starts something, stops something, and waits for a condition. That's exactly what the factories cover:

```java
Command feedUntilLoaded =
    Commands.startEnd(() -> feeder.spin(0.6), () -> feeder.stop(), feeder)
        .until(feeder::hasPiece);
```

- `Commands.startEnd(start, end, feeder)` runs the first lambda once at the start and the second once at the end; the last argument, `feeder`, is its requirement.
- `startEnd` on its own would run forever (it never finishes by itself), so `.until(feeder::hasPiece)` adds the end condition — the same job `isFinished()` did in Step 3. When it ends, the `end` lambda still runs, so the motor still stops.

Same behavior, one statement, no new class.

## Step 5: Compose It With a Back-Off Step

Now add the reverse nudge: spin backward at `-0.2` for a tenth of a second, then stop.

```java
Command backOff =
    Commands.startEnd(() -> feeder.spin(-0.2), () -> feeder.stop(), feeder)
        .withTimeout(0.1);

Command loadPiece = feedUntilLoaded.andThen(backOff);
```

- `withTimeout(0.1)` gives `backOff` its end condition: 0.1 seconds, no matter what.
- `andThen` makes a sequential composition: `backOff` starts only after `feedUntilLoaded` finishes. If the piece never arrives, `feedUntilLoaded` never finishes, and `backOff` never runs — every step of a sequence has to actually finish.
- `loadPiece` is itself just a `Command`, requiring `feeder` for its whole duration — so it can be bound to a button, or composed into something bigger, like any other command.

Once `feedUntilLoaded` and `backOff` are inside `loadPiece`, they belong to that composition — don't also schedule either one on its own.

## Recap

- Override only the lifecycle methods a command actually needs; the rest default to doing nothing (and `isFinished()` defaults to `false`).
- `addRequirements(...)` (or a factory's trailing subsystem argument) declares what the command needs.
- A command with no internal state is usually a one-liner with `Commands.startEnd`, `runOnce`, `run`, etc., plus decorators like `until` and `withTimeout` for end conditions.
- `andThen` builds a sequence out of smaller commands — and the result is still just a command.
