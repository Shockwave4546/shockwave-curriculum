# State Machines: Logic — Worked Example

## Problem

A climber mechanism is always in one of three situations: stowed inside the frame, extending its hook up to the bar, or actively climbing. A teammate tracks this with three booleans, and a bug report says the dashboard once showed the climber as "stowed" and "extending" at the same time. Replace the booleans with a state machine that makes that bug impossible, and design its transitions: the hook extends when the driver presses the climb button, and the climb starts once a sensor reports the hook is at the top. Once the robot is climbing, it stays climbing for the rest of the match.

## Step 1: Plan It First

1. Find out how the boolean version allows the bug.
2. List every state the climber can be in, and make each one an enum constant.
3. Design the transitions: draw the state diagram and write the transition table, with a guard condition for each arrow.
4. Replace the booleans with one field of that enum type, initialized to the start state.
5. Check that changing state is now a single assignment that can't leave two states "on."

## Step 2: See How the Booleans Allow the Bug

```java
private boolean isStowed = true;
private boolean isExtending = false;
private boolean isClimbing = false;
```

Starting to extend should mean turning one flag off and another on:

```java
isExtending = true;
// forgot: isStowed = false;
```

One missed line, and `isStowed` and `isExtending` are both `true`. The compiler can't catch it — as far as Java is concerned, any combination of three booleans is legal, even though only three of the eight combinations make sense.

## Step 3: One Enum Constant per State

```java
public enum ClimberState
{
    STOWED,
    EXTENDING,
    CLIMBING
}
```

Every situation the climber can really be in gets exactly one name, and nothing else is possible. `STOWED` is the start state — the climber really does start the match stowed.

## Step 4: Design the Transitions

Two moves are allowed, each with its own guard condition:

```text
      start
        │
        ▼
  ┌───────────┐  climb button pressed  ┌───────────┐  hook sensor at top  ┌───────────┐
  │  STOWED   │ ─────────────────────▶ │ EXTENDING │ ───────────────────▶ │ CLIMBING  │
  └───────────┘                        └───────────┘                      └───────────┘
```

| From | To | Guard condition |
|---|---|---|
| `STOWED` | `EXTENDING` | the driver presses the climb button |
| `EXTENDING` | `CLIMBING` | the hook sensor reports the hook is at the top |

Check every state for a way out. `STOWED` has one (the driver's button), so the machine can leave its start state. `EXTENDING` has one (the sensor). `CLIMBING` has none — and that's deliberate: once the robot is hanging, it's a **final state** for the rest of the match. Notice also that there's no arrow from `STOWED` straight to `CLIMBING`: a move that isn't in the table can't happen.

## Step 5: One Field, With a Real Starting Value

The three booleans become a single field:

```java
private ClimberState currentState = ClimberState.STOWED;
```

The field starts at the start state, `STOWED`. Leaving it uninitialized would make it `null` — not any of the three states — until something assigned it.

## Step 6: Changing State

Starting to extend is now one assignment:

```java
currentState = ClimberState.EXTENDING;
```

There's no second line to forget. `currentState` held `STOWED`; now it holds `EXTENDING`; it can never hold both, because a variable only holds one value at a time. (When this assignment should happen — only when the `STOWED` → `EXTENDING` guard is true — is Lesson 25.5's job.)

## Step 7: Check It Runs

A quick standalone program confirms the state really is exactly one thing at a time:

```java
public class ClimberStateCheck
{
    public static void main(String[] args)
    {
        ClimberState currentState = ClimberState.STOWED;
        System.out.println(currentState); // STOWED
        currentState = ClimberState.EXTENDING;
        System.out.println(currentState); // EXTENDING
    }
}

enum ClimberState
{
    STOWED,
    EXTENDING,
    CLIMBING
}
```

The public class comes first in the file and the enum after it. That order works on every Java version: Java 25 would also accept the enum first, but on Java 17 running a single file with `java ClimberStateCheck.java` needs the class with `main` to be the first one in the file.

Printing an enum value prints its name, so the output is `STOWED`, then `EXTENDING`.

## Recap

- Several independent booleans allow combinations that make no sense, and the compiler can't stop them.
- An enum lists every real state by name; a single field of that type can only ever hold one of them.
- Draw the diagram and transition table before the code: every arrow gets a guard, and every state needs a way out unless it's a deliberate final state.
- Always initialize the state field to the start state.
- A state change is just an assignment — deciding *when* to make it is Lesson 25.5's job.
