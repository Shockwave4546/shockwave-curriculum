# What Is Command-Based Programming? — Worked Example

## Problem

The drive team wants the robot's LED strip to turn green the moment the indexer detects a game piece, so the driver knows they're loaded without looking away from the field. The indexer already has a method, `indexer.hasPiece()`, that returns `true` while a piece is inside it, and the LED strip is a mechanism, `leds`, with a method `leds.showGreen()`. Write this behavior two ways — imperatively, then declaratively — and compare them.

## Step 1: Plan It First

1. Figure out exactly *when* `showGreen()` should run: once, at the moment `hasPiece()` changes from `false` to `true` — not on every loop while the piece sits there.
2. Write the imperative version: check the condition every loop yourself, and remember whether you've already reacted.
3. Write the declarative version: describe the condition and the action once, and let the library do the checking.
4. Compare what each version asks you to maintain.

## Step 2: The Imperative Version

Without command-based, this code has to live somewhere that runs every loop (every 20ms), and it has to remember whether it already reacted — otherwise it would call `showGreen()` fifty times a second for as long as the piece stays inside:

```java
// Imperative: runs every single loop
if (indexer.hasPiece())
{
    if (!alreadyLit)
    {
        leds.showGreen();
        alreadyLit = true;
    }
}
else
{
    alreadyLit = false;
}
```

`alreadyLit` is a `boolean` field you have to declare, keep correct, and reset in the `else` branch — and if you forget the reset, the LEDs will never light for the *second* game piece of the match.

## Step 3: The Declarative Version

With command-based, you describe the same behavior once, during setup:

```java
// Declarative: written once, during setup
new Trigger(indexer::hasPiece)
    .onTrue(leds.run(coroutine -> leds.showGreen()).named("Show Green"));
```

Read it left to right:

- `new Trigger(indexer::hasPiece)` — wraps the condition. `indexer::hasPiece` is a method reference (Lesson 19.1) standing in for `() -> indexer.hasPiece()`.
- `.onTrue(...)` — "when this condition becomes true."
- `leds.run(coroutine -> leds.showGreen())` — the action: a command whose body calls `showGreen()` once. The body has no loop, so the command ends right after that call. Because it's built with the LED mechanism's own `run(...)`, the command **requires** `leds` — while it runs, no other command can drive the LED strip.
- `.named("Show Green")` — every v3 command has a name; the command isn't finished until it gets one.

There's no `alreadyLit` flag anywhere. The Scheduler checks the condition every loop on your behalf, and `onTrue` only reacts to the change from `false` to `true` — exactly what Step 2's flag was hand-building.

## Step 4: Compare

| | Imperative | Declarative |
|---|---|---|
| Where it lives | Code that runs every loop | Setup code that runs once |
| Extra state you maintain | `alreadyLit` flag, plus its reset | None |
| Adding a second sensor-to-LED rule | Another copy of the whole flag pattern | One more line |

## Recap

- Imperative code says *how* to check, every loop, and makes you track edge-detection state (like `alreadyLit`) by hand.
- Declarative command-based code says *what* should happen under *what* condition, once — the scheduler handles the checking.
- A `Trigger` wraps the condition; a named command (here, from `leds.run(...).named(...)`) is the action.
- Building the command from the LED mechanism's own `run(...)` means it automatically requires `leds`, so no other command can fight it for the LED strip. Lesson 25.2 covers how commands are built in detail.
