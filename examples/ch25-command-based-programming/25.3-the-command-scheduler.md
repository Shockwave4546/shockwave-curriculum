# The Command Scheduler — Worked Example

## Problem

A `Shooter` mechanism stores the flywheel's measured speed in a field, `measuredRpm`, which its `refreshRpm()` method copies from the encoder. During setup, the team registers that refresh as a side job, so it happens once every loop:

```java
Scheduler.getDefault().addPeriodic(() -> shooter.refreshRpm());
```

The shooter's `spinUpCommand()` starts the flywheel and finishes once `getRpm()` (which returns `measuredRpm`) reaches 4000:

```java
public Command spinUpCommand()
{
    return run(coroutine -> {
        motor.setThrottle(1.0);
        while (getRpm() < 4000)
        {
            coroutine.yield();
        }
    }).named("Spin Up");
}
```

A trigger binds `spinUpCommand()` with `onTrue` to a button, and the shooter has no default command. The driver presses the button right before loop 1. The encoder reads 0 RPM on loop 1, 2500 RPM on loop 2, and 4100 RPM on loop 3. Trace what the scheduler does on each loop, and find the loop on which Spin Up finishes.

## Step 1: Plan It First

1. Confirm the scheduler is actually being run every loop.
2. Write down the steps of one scheduler loop, in order.
3. Walk through loops 1, 2, and 3, one step at a time, keeping track of where Spin Up's body is paused.
4. Check which RPM value the loop condition sees on each loop.

## Step 2: Make Sure the Scheduler Runs

None of this happens unless `robotPeriodic()` runs the scheduler:

```java
@Override
public void robotPeriodic()
{
    Scheduler.getDefault().run();
}
```

Every call to `run()` is one full loop of the scheduler: all six steps, in order.

## Step 3: The Six Steps, in Order

1. Clean up ended scopes (nothing to clean up in this example).
2. Run side jobs — here, `shooter.refreshRpm()`.
3. Poll triggers — a binding whose condition changed queues its command.
4. Queue default commands for free mechanisms.
5. Start queued commands, settling any conflicts.
6. Run each running command until it yields or finishes.

## Step 4: Trace Each Loop

**Loop 1** (encoder reads 0):

- Step 2: `refreshRpm()` sets `measuredRpm` to 0.
- Step 3: the button has just been pressed, so `onTrue` queues Spin Up. It hasn't started yet.
- Step 4: Spin Up is queued for the shooter, so there's nothing to do (and the shooter has no default command anyway).
- Step 5: Spin Up moves from the queue to the running set. Nothing else needs the shooter, so there's no conflict.
- Step 6: Spin Up's body runs for the first time: `motor.setThrottle(1.0)` starts the flywheel, then the loop condition checks 0 < 4000 — `true` — so the body reaches `coroutine.yield()` and pauses there.

**Loop 2** (encoder reads 2500):

- Step 2: `refreshRpm()` sets `measuredRpm` to 2500.
- Step 3: the button is still held, but `onTrue` only reacts to the press itself — nothing new is queued.
- Steps 4-5: the shooter is busy with Spin Up; nothing to queue or start.
- Step 6: Spin Up resumes right after its `yield()`, and the loop condition checks 2500 < 4000 — `true` — so it yields again.

**Loop 3** (encoder reads 4100):

- Step 2: `refreshRpm()` sets `measuredRpm` to 4100.
- Steps 3-5: nothing new.
- Step 6: Spin Up resumes; the loop condition checks 4100 < 4000 — `false` — so the `while` loop ends. There's no code after the loop, so the body returns and Spin Up is **finished**, freeing the shooter.

**Answer:** Spin Up finishes on loop 3, during step 6. The flywheel keeps spinning at full throttle afterward — the body never turned it off — which is exactly what "spin up and stay up to speed" should do.

## Step 5: Why the Order Mattered

On loop 3, the loop condition saw 4100, not last loop's 2500 — because side jobs (step 2) always run before commands (step 6). If the refresh ran *after* the commands, Spin Up would have checked a stale 2500, yielded one extra time, and finished on loop 4 instead.

Notice also that the button press on loop 1 didn't start Spin Up the instant the trigger was polled: step 3 only *queued* it, step 5 started it, and step 6 gave it its first turn — all within that same loop. And because the refresh is a side job, not a command, it never requires the shooter, so it can't conflict with Spin Up; it only updates data, never the motor.

## Recap

- `Scheduler.getDefault().run()` in `robotPeriodic()` is what makes every loop happen at all.
- Each loop: clean up scopes → side jobs (`addPeriodic`) → poll triggers (which queue commands) → queue default commands → start queued commands → run each command until it yields or finishes.
- A command's body pauses at `coroutine.yield()` and resumes from that exact spot on the next loop; it finishes when the body returns.
- Because side jobs run before commands, commands always act on this loop's freshly updated data.
