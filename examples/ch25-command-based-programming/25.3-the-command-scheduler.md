# The Command Scheduler — Worked Example

## Problem

A `ShooterSubsystem` stores the flywheel's measured speed in a field, `measuredRpm`, which its `periodic()` method refreshes from the encoder every loop. A `SpinUp` command starts the flywheel in `initialize()` and finishes once `shooter.getRpm()` reaches 4000. A trigger schedules `SpinUp` when the driver presses a button.

The driver presses the button right before loop 1. The encoder reads 0 RPM on loop 1, 2500 RPM on loop 2, and 4100 RPM on loop 3. Trace exactly what the scheduler calls on each loop, and find the loop on which `SpinUp` ends.

## Step 1: Plan It First

1. Confirm the scheduler is actually being run every loop.
2. Write down the four steps of one scheduler iteration, in order.
3. Walk through loops 1, 2, and 3, one step at a time.
4. Check which RPM value `isFinished()` sees on each loop.

## Step 2: Make Sure the Scheduler Runs

None of this happens unless `robotPeriodic()` runs the scheduler:

```java
@Override
public void robotPeriodic()
{
    CommandScheduler.getInstance().run();
}
```

Every call to `run()` is one full iteration: all four steps, in order.

## Step 3: The Four Steps, in Order

1. Every registered subsystem's `periodic()`.
2. Poll triggers — newly scheduled commands get `initialize()` right away.
3. For each scheduled command: `execute()`, then `isFinished()` — if `true`, `end(false)` and free its requirements.
4. Schedule default commands for any subsystem that's now free.

## Step 4: Trace Each Loop

**Loop 1** (encoder reads 0):

- Step 1: `shooter.periodic()` sets `measuredRpm` to 0.
- Step 2: the trigger's condition has just become true, so `SpinUp` is scheduled, and `SpinUp.initialize()` runs immediately — the flywheel starts.
- Step 3: `SpinUp` is now scheduled, so it runs in this same loop: `SpinUp.execute()`, then `SpinUp.isFinished()` checks 0 ≥ 4000 — `false`, so it stays scheduled.
- Step 4: the shooter is claimed by `SpinUp`, so no default command is needed.

**Loop 2** (encoder reads 2500):

- Step 1: `shooter.periodic()` sets `measuredRpm` to 2500.
- Step 2: nothing new to schedule — `SpinUp` is already running.
- Step 3: `SpinUp.execute()`, then `isFinished()` checks 2500 ≥ 4000 — `false`.
- Step 4: still claimed, nothing to do.

**Loop 3** (encoder reads 4100):

- Step 1: `shooter.periodic()` sets `measuredRpm` to 4100.
- Step 2: nothing new to schedule.
- Step 3: `SpinUp.execute()`, then `isFinished()` checks 4100 ≥ 4000 — `true`. The scheduler calls `SpinUp.end(false)` (`false` because it finished on its own, not because something interrupted it) and removes it, freeing the shooter.
- Step 4: the shooter is free now, but it has no default command, so nothing is scheduled.

**Answer:** `SpinUp` ends on loop 3, with `end(false)`.

## Step 5: Why the Order Mattered

On loop 3, `isFinished()` saw 4100, not last loop's 2500 — because Step 1 (`periodic()`) always runs before Step 3 (commands). If commands ran first, `SpinUp` would have checked a stale 2500, stayed scheduled one extra loop, and ended on loop 4 instead.

Notice also that `initialize()` ran during Step 2 of loop 1 — the moment `SpinUp` was *scheduled* — not at some separate time; and because it was scheduled before Step 3, it got its first `execute()` in that very same loop.

## Recap

- `CommandScheduler.getInstance().run()` in `robotPeriodic()` is what makes every loop's iteration happen at all.
- Each iteration: subsystem `periodic()` → poll triggers (and `initialize()` newly scheduled commands) → `execute()`/`isFinished()` each scheduled command → default commands for free subsystems.
- A command that finishes on its own gets `end(false)`; its requirements are freed in that same step.
- Because `periodic()` runs first, commands always act on this loop's freshly updated subsystem state.
