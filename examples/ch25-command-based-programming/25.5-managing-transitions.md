# Managing Transitions — Worked Example

## Problem

An `Elevator` mechanism has four states, stored in a `currentState` field that starts at `LOWERED`:

```java
public enum ElevatorState
{
    LOWERED,
    RAISING,
    AT_TOP,
    LOWERING
}
```

Its design, as a transition table:

| From | To | Guard condition |
|---|---|---|
| `LOWERED` | `RAISING` | the operator presses the raise button |
| `RAISING` | `AT_TOP` | the top limit switch is pressed |
| `AT_TOP` | `LOWERING` | the operator presses the lower button |
| `LOWERING` | `LOWERED` | the bottom limit switch is pressed |

The state actions: the motor gets `0.0` when `LOWERED`, `0.6` while `RAISING`, a gentle `0.05` to hold position `AT_TOP`, and `-0.3` while `LOWERING`. Write the elevator's `update()` method and the command that runs it every loop, then trace four loops starting from `LOWERED`.

## Step 1: Plan It First

1. Put one arrow-form `switch` over `currentState` inside `update()`: one case per state.
2. In each case, set the motor for that state, then check only that state's guard.
3. Route every transition through an `enter(...)` method, so the change is logged once.
4. Wrap `update()` in a lowest-priority `runRepeatedly` command to use as the default command.
5. Trace four loops to check it.

## Step 2: One Case per State, With Its Own Guard

`motor` is a `DriveMotor` (Ch.4), `topLimit` and `bottomLimit` are `DigitalInput`s, and `raiseButton` and `lowerButton` are `BooleanSupplier`s handed to the elevator's constructor. The `RAISING` case shows the shape every case follows — action first, then that state's guard:

```java
case RAISING ->
{
    motor.setThrottle(0.6);
    if (topLimit.get())
    {
        enter(ElevatorState.AT_TOP);
    }
}
```

The top limit switch only matters while the elevator is moving up, so its check goes inside `RAISING` — and nowhere else. If it were placed in the `LOWERED` case instead, it would never be reached while the elevator is actually rising, and the elevator would drive into its hard stop.

## Step 3: The Whole `update()` and `enter()`

```java
private void update()
{
    switch (currentState)
    {
        case LOWERED ->
        {
            motor.setThrottle(0.0);
            if (raiseButton.getAsBoolean())
            {
                enter(ElevatorState.RAISING);
            }
        }
        case RAISING ->
        {
            motor.setThrottle(0.6);
            if (topLimit.get())
            {
                enter(ElevatorState.AT_TOP);
            }
        }
        case AT_TOP ->
        {
            motor.setThrottle(0.05); // gentle hold
            if (lowerButton.getAsBoolean())
            {
                enter(ElevatorState.LOWERING);
            }
        }
        case LOWERING ->
        {
            motor.setThrottle(-0.3);
            if (bottomLimit.get())
            {
                enter(ElevatorState.LOWERED);
            }
        }
    }
}

private void enter(ElevatorState next)
{
    System.out.println("Elevator: " + currentState + " -> " + next);
    currentState = next;
}
```

Each row of the transition table became exactly one `if`, inside the case for its "From" state. Every state has a way out, including the start state, `LOWERED`, which leaves when the operator presses the raise button.

## Step 4: Run It Every Loop as the Default Command

```java
public Command stateMachineCommand()
{
    return runRepeatedly(this::update)
        .withPriority(Command.LOWEST_PRIORITY)
        .named("Elevator State Machine");
}
```

Installed once during setup with `elevator.setDefaultCommand(elevator.stateMachineCommand());`, this calls `update()` once per scheduler loop whenever no other command needs the elevator. Its lowest priority means a manual override — say, a "hold still" command the operator can trigger if something jams — takes over the elevator immediately; `currentState` keeps its value, and the machine resumes from it once the override ends.

## Step 5: Trace Four Loops

The elevator starts `LOWERED`. The raise button is pressed on loops 2-4; the top limit switch reads `false` on loops 1-3 and `true` on loop 4.

| Loop | State at start | Motor set to | Guard checked | Guard value | State at end |
|---|---|---|---|---|---|
| 1 | `LOWERED` | `0.0` | raise button | `false` | `LOWERED` |
| 2 | `LOWERED` | `0.0` | raise button | `true` | `RAISING` |
| 3 | `RAISING` | `0.6` | top limit | `false` | `RAISING` |
| 4 | `RAISING` | `0.6` | top limit | `true` | `AT_TOP` |

On loop 2, the motor was still set to `0.0` — that line ran before the guard — and the new state only takes effect on loop 3, one loop (20ms) later. The same thing happens on loop 4: the motor gets `0.6` one last time, and the gentle hold of `AT_TOP` starts on loop 5. That's the normal rhythm of a state machine run once per loop: act on the current state, decide the next one, and let the next loop act on it. The console shows exactly two lines, one per transition: `Elevator: LOWERED -> RAISING`, then `Elevator: RAISING -> AT_TOP`.

Notice that on loop 3 the raise button is still held, but nothing happens because of it: only the `LOWERED` case checks that guard, and the machine isn't in `LOWERED` anymore.

## Recap

- An arrow-form `switch` over the state field runs one case per state: the state's action, then only that state's guards.
- Every transition goes through `enter(...)`, so each change is logged once, as an entry action.
- The `switch` runs every loop as a lowest-priority default command, so any other command can take over the mechanism without losing the current state.
- A transition takes effect on the next loop: this loop acts on the old state, and the next loop acts on the new one.
