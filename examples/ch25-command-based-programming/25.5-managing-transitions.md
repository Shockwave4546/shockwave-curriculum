# Managing Transitions — Worked Example

## Problem

An `ElevatorSubsystem` has three states, stored in a `currentState` field:

```java
public enum ElevatorState
{
    LOWERED,
    RAISING,
    AT_TOP
}
```

Write its `periodic()` method so that each state drives the motor correctly — `0.0` when `LOWERED`, `0.6` while `RAISING`, and a gentle `0.05` to hold position when `AT_TOP` — and so that the elevator moves from `RAISING` to `AT_TOP` on its own the moment its top limit switch is pressed. Then trace what happens over three loops, starting while the elevator is `RAISING`.

## Step 1: Plan It First

1. Put one `switch` over `currentState` inside `periodic()`, so it runs every scheduler loop.
2. Give each state its own `case` that sets the motor.
3. Put the transition check inside the one `case` it belongs to: `RAISING`.
4. End every `case` with `break;`.
5. Trace three loops to check it.

## Step 2: One Case per State

Each `case` runs that state's behavior. `motor` and `topLimitSwitch` stand for the subsystem's motor controller and limit switch objects:

```java
case LOWERED:
    motor.set(0.0);
    break;
case AT_TOP:
    motor.set(0.05); // gentle hold
    break;
```

## Step 3: Put the Transition in the Right Case

The limit switch only matters while the elevator is moving up, so the check goes inside `RAISING` — and nowhere else:

```java
case RAISING:
    motor.set(0.6);
    if (topLimitSwitch.get())
    {
        currentState = ElevatorState.AT_TOP; // transition
    }
    break;
```

The transition is just an assignment to the state field. If this check were placed in the `LOWERED` case instead, it would never be reached while the elevator is actually rising — and the elevator would drive into its hard stop.

## Step 4: The Whole `periodic()`

```java
@Override
public void periodic()
{
    switch (currentState)
    {
        case LOWERED:
            motor.set(0.0);
            break;
        case RAISING:
            motor.set(0.6);
            if (topLimitSwitch.get())
            {
                currentState = ElevatorState.AT_TOP;
            }
            break;
        case AT_TOP:
            motor.set(0.05);
            break;
    }
}
```

## Step 5: Trace Three Loops

The elevator starts `RAISING`. The limit switch reads `false` on loop 1 and `true` on loops 2 and 3.

| Loop | State at start | Case that runs | Motor set to | Limit switch | State at end |
|---|---|---|---|---|---|
| 1 | `RAISING` | `RAISING` | `0.6` | `false` | `RAISING` |
| 2 | `RAISING` | `RAISING` | `0.6` | `true` | `AT_TOP` |
| 3 | `AT_TOP` | `AT_TOP` | `0.05` | `true` | `AT_TOP` |

On loop 2, the motor was still set to `0.6` (that line ran before the check), and the new state only takes effect on loop 3 — one loop, 20ms later. That's the normal rhythm of a `periodic()` state machine: act on the current state, decide the next one, and let the next loop act on it.

## Step 6: What a Missing `break;` Would Do

Suppose the `break;` at the end of `RAISING` were deleted. After `RAISING`'s code runs, execution would fall straight through into the `AT_TOP` case's code in the same loop and set the motor to `0.05` — running two states' behavior back to back. And it would happen on *every* `RAISING` loop, not just the one with the transition: on loop 1, `0.6` would be overwritten with `0.05` right away, so the elevator would never actually rise. Every `case` needs its `break;`.

## Recap

- A `switch` over the state field inside `periodic()` runs every loop: one `case` per state.
- Each `case` does its state's behavior and checks only the transitions that belong to that state.
- A transition is a plain reassignment of the state field; the next loop acts on the new state.
- A missing `break;` makes one case fall through into the next, running the wrong state's behavior too.
