# Recursive Searching and Sorting — Worked Example

## Problem

The shooter's lookup table stores its RPM setpoints in a sorted array. Use recursive binary search to find where 4000 RPM is stored and to confirm that 2750 RPM isn't in the table, tracing every recursive call. Then trace how merge sort splits and merges a separate, unsorted list of four practice-shot RPM readings.

## Step 1: Plan It First

1. Recursive binary search: pass the range `start`..`end` as parameters, and halve it with each call.
2. It needs two base cases: an empty range (not found) and a match at the middle.
3. Trace a search that finds its target and a search that doesn't.
4. Merge sort: split down to single elements (the base case), then merge the sorted halves back together.

```java
int[] rpmTable = {1500, 2000, 2500, 3000, 3500, 4000, 4500};
```

## Step 2: Write the Recursive Binary Search

```java
public static int findSetpoint(int[] table, int start, int end, int target)
{
    if (end < start)                  // base case 1: empty range — not found
    {
        return -1;
    }
    int middle = (start + end) / 2;
    if (target == table[middle])      // base case 2: found it
    {
        return middle;
    }
    else if (target < table[middle])
    {
        return findSetpoint(table, start, middle - 1, target); // left half
    }
    else
    {
        return findSetpoint(table, middle + 1, end, target);   // right half
    }
}
```

The first call covers the whole array, indexes `0` through `rpmTable.length - 1`:

```java
System.out.println(findSetpoint(rpmTable, 0, rpmTable.length - 1, 4000)); // 5
System.out.println(findSetpoint(rpmTable, 0, rpmTable.length - 1, 2750)); // -1
```

## Step 3: Trace a Search That Finds Its Target (4000)

| Call | `start` | `end` | `middle` | `table[middle]` | What happens |
|---|---|---|---|---|---|
| `findSetpoint(rpmTable, 0, 6, 4000)` | 0 | 6 | 3 | 3000 | 4000 > 3000, so call on the right half |
| `findSetpoint(rpmTable, 4, 6, 4000)` | 4 | 6 | 5 | 4000 | match (base case 2), return `5` |

The second call returns `5` to the first call. The first call was executing `return findSetpoint(...)`, so it passes that same `5` straight back to `main`.

## Step 4: Trace a Search That Doesn't Find Its Target (2750)

| Call | `start` | `end` | `middle` | `table[middle]` | What happens |
|---|---|---|---|---|---|
| `findSetpoint(rpmTable, 0, 6, 2750)` | 0 | 6 | 3 | 3000 | 2750 < 3000, so call on the left half |
| `findSetpoint(rpmTable, 0, 2, 2750)` | 0 | 2 | 1 | 2000 | 2750 > 2000, so call on the right half |
| `findSetpoint(rpmTable, 2, 2, 2750)` | 2 | 2 | 2 | 2500 | 2750 > 2500, so call on the right half |
| `findSetpoint(rpmTable, 3, 2, 2750)` | 3 | 2 | — | — | `end < start` (base case 1), return `-1` |

The fourth call's range starts at 3 and ends at 2, so it's empty. This is where the `end < start` check matters. Without it, the method would keep computing a `middle` and recursing into ranges that hold nothing. That `-1` is passed back up through all three waiting calls.

## Step 5: Trace Merge Sort

Now sort four practice-shot readings with the lesson's `mergeSort`. Its `mergeSortHelper` sorts the left half, then the right half, then calls `merge` to combine them:

```java
int[] shotRpms = {3000, 700, 4800, 1200};
mergeSort(shotRpms);
```

Split and merge, using the same nested-brace notation as the lesson:

```
Split:  { {3000, 700} , {4800, 1200} }
Split:  { { {3000}, {700} } , { {4800}, {1200} } }   <- single elements: base case reached
Merge:  { {700, 3000} , {1200, 4800} }
Merge:  { 700, 1200, 3000, 4800 }
```

`mergeSortHelper` finishes the entire left half before it starts on the right half. So the three `merge` calls happen in this order, and the array (sorted in place) looks like this after each one:

| `merge` call | Range merged | `shotRpms` afterward |
|---|---|---|
| 1 | indexes 0-1 (`{3000}` + `{700}`) | `{700, 3000, 4800, 1200}` |
| 2 | indexes 2-3 (`{4800}` + `{1200}`) | `{700, 3000, 1200, 4800}` |
| 3 | indexes 0-3 (`{700, 3000}` + `{1200, 4800}`) | `{700, 1200, 3000, 4800}` |

The final merge takes values from both halves in turn: `700` from the left, `1200` from the right, `3000` from the left, then `4800` from the right. That only works because both halves were already sorted when it started. Guaranteeing that is the job of the two recursive calls.

## Recap

- Recursive binary search passes the shrinking range (`start`, `end`) as parameters. That range plays the same role the `left`/`right` loop variables and `while` condition play in the iterative version.
- It needs both base cases: a match at `middle`, and an empty range (`end < start`) for a target that isn't there.
- Each recursive call returns its result straight back up to the call that made it.
- Merge sort splits down to single elements (already sorted, the base case), sorts the left half completely, then the right half, and only then merges them.
- The merge step depends on both halves already being sorted, which is exactly what the recursive calls before it guarantee.
