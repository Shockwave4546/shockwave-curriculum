# Overriding Methods — Worked Example

## Problem

Every sensor on the robot has a name and a `report()` method that prints its status. A plain `Sensor` doesn't know how to read anything, so its `report()` just says so. A `LimitSwitch` is a kind of `Sensor` that knows whether it's pressed — it should replace the generic `report()` with its own version that prints the pressed state, while still labeling the line with the sensor's name.

## Step 1: Write the Superclass

`Sensor` holds the name (as a `private` field), a getter for it, and the generic `report()`:

```java
class Sensor
{
    private String name;

    public Sensor(String name)
    {
        this.name = name;
    }

    public String getName()
    {
        return name;
    }

    public void report()
    {
        System.out.println(name + ": no reading available");
    }
}
```

## Step 2: Write the Subclass and Override `report()`

`LimitSwitch extends Sensor`, so it inherits `getName()` and `report()` unchanged. To *replace* `report()`, it declares a method with the exact same signature — same name, same (empty) parameter list, same `void` return type — marked with `@Override`:

```java
class LimitSwitch extends Sensor
{
    private boolean pressed;

    public LimitSwitch(String name, boolean pressed)
    {
        super(name);
        this.pressed = pressed;
    }

    @Override
    public void report()
    {
        System.out.println(getName() + ": pressed = " + pressed);
    }
}
```

Notice the override uses `getName()`, not `name`. `name` is `private` in `Sensor`, so even a subclass can't touch it directly — the inherited public getter is the only way in.

## Step 3: Put It Together in `main`

```java
public class SensorReport
{
    public static void main(String[] args)
    {
        Sensor sparePort = new Sensor("Spare port");
        LimitSwitch armStop = new LimitSwitch("Arm limit", true);

        sparePort.report();
        armStop.report();
    }
}

class Sensor
{
    private String name;

    public Sensor(String name)
    {
        this.name = name;
    }

    public String getName()
    {
        return name;
    }

    public void report()
    {
        System.out.println(name + ": no reading available");
    }
}

class LimitSwitch extends Sensor
{
    private boolean pressed;

    public LimitSwitch(String name, boolean pressed)
    {
        super(name);
        this.pressed = pressed;
    }

    @Override
    public void report()
    {
        System.out.println(getName() + ": pressed = " + pressed);
    }
}
```

All three classes live in one file, `SensorReport.java`. Only `SensorReport` is `public` (a file can have at most one `public` top-level class, and it must match the file name), and it comes first so the program runs on Java 17 as well as Java 25 (see worked example 17.1); `Sensor` and `LimitSwitch` sit alongside it without `public`.

## What It Prints

```
Spare port: no reading available
Arm limit: pressed = true
```

`sparePort` is a plain `Sensor`, so it runs `Sensor`'s `report()`. `armStop` is a `LimitSwitch`, so its own override runs instead — the inherited version is replaced, not run as well.

## Step 4: Why `@Override` Is Worth Writing

Suppose the override's name had been mistyped as `reprot()`. With `@Override` in place, the compiler refuses the program:

```
error: method does not override or implement a method from a supertype
    @Override
    ^
```

Delete `@Override` and keep the typo, and the program compiles and runs — but now `reprot()` is a brand-new, unrelated method, and `LimitSwitch` still inherits `Sensor`'s `report()` unchanged:

```
Spare port: no reading available
Arm limit: no reading available
```

Nothing crashes and nothing warns you; the limit switch just quietly never reports its real state. `@Override` turns that silent bug into an error you can't miss.

## Step 5: Override vs. Overload, One More Time

If `LimitSwitch` had instead declared `public void report(int repeatCount)`, that would be an **overload** — same name, different parameter list — not an override. `LimitSwitch` would then have *two* `report` methods: the inherited `report()` (still `Sensor`'s version) and the new `report(int)`. Calling `armStop.report()` would print `Arm limit: no reading available`. Only an exact signature match replaces the inherited method.

## Recap

- An override declares a method with the same name and parameter list as the inherited one, and the same return type (or a subtype of it), replacing the superclass's version for that subclass.
- Always mark overrides with `@Override` — a typo in the name becomes a compile error instead of a silently unrelated new method.
- Changing the parameter list makes an overload, not an override; the inherited method stays in place alongside it.
- A subclass reaches its superclass's `private` fields only through inherited getters/setters, even inside its own overrides.
