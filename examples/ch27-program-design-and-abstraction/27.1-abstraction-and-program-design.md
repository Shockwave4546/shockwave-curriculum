# Abstraction and Program Design — Worked Example

## Problem

The pit crew describes what they need: "Each **battery** has a **label** and a **voltage**. Before a match, we need to know whether a battery is ready — at least 12.5 volts — and how many batteries we're tracking in total." Design the class this program needs *before* writing any Java, then write it, then change how the readiness check works internally without breaking the code that uses it.

## Step 1: Find the Nouns

Reading the description for nouns gives: *battery*, *label*, *voltage*, *match*, *pit crew*.

- **Battery** is the thing the program is actually about — it gets its own class.
- **Label** and **voltage** are nouns too, but they describe a battery rather than standing on their own — they become the `Battery` class's attributes, not classes of their own.
- **Match** and **pit crew** are context: the program never has to store or do anything with them, so they don't need classes here.

The nouns-become-classes trick is a starting point, not an automatic rule — each noun still gets a quick "does the program actually need to store or do something with this?" check.

## Step 2: Sketch It as a UML Class Diagram

Before any Java, a quick box sketch — `-` for private members, `+` for public ones:

```
+---------------------------------------------+
| Battery                                     |
+---------------------------------------------+
| - label : String                            |
| - voltage : double                          |
| - batteriesTracked : int   (static)         |
+---------------------------------------------+
| + Battery(label : String, voltage : double) |
| + getLabel() : String                       |
| + isMatchReady() : boolean                  |
+---------------------------------------------+
```

This sketch already shows both kinds of **data abstraction** vocabulary from Ch.7: `label` and `voltage` are **instance variables** (every battery has its own), while `batteriesTracked` is a **class/static variable** (one shared count for all of them). It also shows the one piece of **procedural abstraction** the problem calls for: `isMatchReady()` — a named answer to "is this battery ready?", with no hint yet of *how* it decides. (The "(static)" note is just an informal whiteboard label, not official UML notation.)

## Step 3: Write the Class From the Sketch

```java
public class Battery
{
    private String label;
    private double voltage;
    private static int batteriesTracked = 0;

    public Battery(String label, double voltage)
    {
        this.label = label;
        this.voltage = voltage;
        batteriesTracked++;
    }

    public String getLabel()
    {
        return label;
    }

    public boolean isMatchReady()
    {
        return voltage >= 12.5;
    }

    public static void main(String[] args)
    {
        Battery batteryA = new Battery("2026-A", 12.8);
        Battery batteryC = new Battery("2026-C", 12.1);

        System.out.println(batteryA.getLabel() + " ready: " + batteryA.isMatchReady());
        System.out.println(batteryC.getLabel() + " ready: " + batteryC.isMatchReady());
        System.out.println("Batteries tracked: " + batteriesTracked);
    }
}
```

Every line traces straight back to the sketch: the three fields, the constructor, and the two public methods. Each constructor call bumps the one shared `batteriesTracked`, while each object keeps its own `label` and `voltage`.

## What It Prints

```
2026-A ready: true
2026-C ready: false
Batteries tracked: 2
```

`12.8 >= 12.5` is `true`; `12.1 >= 12.5` is `false`. Two `Battery` objects were constructed, so the shared count is `2`.

## Step 4: Change *How* Without Changing *What*

A teammate points out that the bare `12.5` inside `isMatchReady()` is a magic number (Ch.26's DRY). Rewrite the method's internals to use a named constant instead:

```java
private static final double MIN_MATCH_VOLTAGE = 12.5;

public boolean isMatchReady()
{
    return voltage >= MIN_MATCH_VOLTAGE;
}
```

Add the constant alongside the other fields and replace the old `isMatchReady()` with this version; nothing else in the class changes. `main` still calls `batteryA.isMatchReady()` exactly as before, and the program prints exactly the same three lines as in Step 3.

That's procedural abstraction's real payoff: the method's name, parameters, return type, and observable behavior all stayed the same, so no caller had to change — even though its implementation did. `main` only ever depended on *what* `isMatchReady()` answers, never on *how* it works it out.

## Recap

- Start design by reading the problem for nouns, then check each one: a real thing the program manages becomes a class; a noun that just describes that thing becomes one of its attributes.
- A rough UML sketch (`-` private, `+` public) is enough to lay out attributes and methods before writing Java.
- Instance variables hold each object's own data; a static variable holds one value shared by every object — both are data abstraction in practice.
- A well-named method lets callers use *what* it does without knowing *how* — so its internals can change freely as long as its signature and behavior stay the same.
