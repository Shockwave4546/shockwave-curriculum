# Methods: Passing & Returning References of an Object — Worked Example

**Outline ref:** 7.3 — Methods: Passing/Returning References of an Object (CSA 3.6)
**Pairs with:** [`lessons/ch07-the-class-blueprint/7.3-methods-passing-and-returning-references-of-an-object.md`](../../lessons/ch07-the-class-blueprint/7.3-methods-passing-and-returning-references-of-an-object.md)
**Status:** new — authored worked example (fully solved, walked step by step — not a problem to attempt)

## Problem

A `Robot` class has a `FieldPosition` (x/y coordinates on the field, in inches) as its starting position. Show what goes wrong if the constructor and the getter just hand the reference around, then fix both.

## Step 1: The Has-A Relationship

```java
class FieldPosition
{
    private double xInches;
    private double yInches;

    public FieldPosition(double initX, double initY)
    {
        xInches = initX;
        yInches = initY;
    }

    public double getX()
    {
        return xInches;
    }

    public double getY()
    {
        return yInches;
    }

    public void setX(double newX)
    {
        xInches = newX;
    }
}
```

```java
class Robot
{
    private String name;
    private FieldPosition startingPosition; // instance variable of type FieldPosition

    public FieldPosition getStartingPosition()
    {
        return startingPosition;
    }
}
```

`Robot` has-a `FieldPosition`.

## Step 2: A Constructor That Just Stores the Reference

```java
public Robot(String initName, FieldPosition initPosition)
{
    name = initName;
    startingPosition = initPosition; // stores the SAME reference the caller passed in
}
```

## Step 3: Watch It Go Wrong

Java is always call by value — but for an object, the value copied is the reference, not the object. So `startingPosition` and whatever `FieldPosition` the caller passed in are the *same* object:

```java
FieldPosition start = new FieldPosition(54.0, 27.0);
Robot robot = new Robot("Shockwave-1622", start);

start.setX(0.0); // caller changes ITS OWN variable...

System.out.println(robot.getStartingPosition().getX()); // ...but this prints 0.0!
```

The robot's "starting position" just silently changed, even though nothing ever called a method on `robot` itself. That's because `robot`'s `startingPosition` was never a separate copy — it's the exact same `FieldPosition` object `start` still points to.

## Step 4: Fix the Constructor With a Defensive Copy

Instead of storing the reference handed in, build a brand-new `FieldPosition` with the same values:

```java
public Robot(String initName, FieldPosition initPosition)
{
    name = initName;
    // Defensive copy — a new FieldPosition with the same values,
    // not the same object
    startingPosition = new FieldPosition(initPosition.getX(), initPosition.getY());
}
```

Now mutating the caller's original `start` object afterward has zero effect on `robot`'s own `startingPosition`.

## Step 5: The Same Problem Is Still Waiting on the Way Out

The constructor is fixed, but `getStartingPosition()` from Step 1 still returns `startingPosition` directly — a live reference to the robot's real internal object:

```java
FieldPosition p = robot.getStartingPosition();
p.setX(999.0); // this actually changes robot's real startingPosition!
```

## Step 6: Fix the Getter, Too

Return a copy instead of the real object:

```java
public FieldPosition getStartingPosition()
{
    return new FieldPosition(startingPosition.getX(), startingPosition.getY());
}
```

Now neither the constructor nor the getter ever leaks a reference to `robot`'s actual internal `FieldPosition` — every value that goes in or comes out is a separate copy.

## Step 7: Chaining, Now That the Getter Is Safe

```java
double startX = robot.getStartingPosition().getX();
```

`getStartingPosition()` returns a `FieldPosition`, and `FieldPosition` has a `getX()` — so the chain compiles. If `getStartingPosition()` returned, say, a `String`, `.getX()` on the end would fail to compile, since `String` has no such method.

## Recap

- `Robot` has-a `FieldPosition` — an object can be another object's instance variable.
- Passing or returning `startingPosition` copies its *reference*, not the object — the broken version in Steps 2–3 left `robot` and the caller pointing at the same `FieldPosition`.
- Because `FieldPosition` is mutable (it has `setX`), both the constructor and the getter needed a defensive copy so outside code can't reach in and change `robot`'s real data later.
- `robot.getStartingPosition().getX()` is chaining — it only compiles because `getStartingPosition()`'s return type, `FieldPosition`, actually has a `getX()` method.
