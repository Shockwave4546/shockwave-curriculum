# Inheritance, Superclass, Subclass — Exercises

## Multiple Choice

**Question:** A teammate is deciding where to use `extends`. Which of these is a genuine is-a relationship, where `extends` is the right choice?

**Options:**

- A. `class Shooter extends Flywheel` — because a shooter contains a flywheel
- B. `class BrushlessMotor extends Motor` — because a brushless motor is a kind of motor
- C. `class Robot extends Battery` — because a robot runs on a battery
- D. `class SwerveModule extends Drivetrain` — because a drivetrain is built from swerve modules

**Answer:** B

**Why:** Apply the substitution test: anywhere the code expects "a motor," a brushless motor makes complete sense — it really is a specialized kind of motor. That's is-a, which is exactly what `extends` models.

- A is wrong — a shooter *has a* flywheel as one of its parts; a shooter isn't a kind of flywheel. That's has-a, so `Shooter` should hold a `Flywheel` field instead.
- C is wrong — a robot *has a* battery. A robot wouldn't make sense anywhere the code expects "a battery," so the substitution test fails.
- D is wrong — a swerve module is one *part* of a drivetrain, not a kind of drivetrain. The drivetrain *has* swerve modules (has-a); a single module can't stand in anywhere a whole drivetrain is expected.

## Micro-Parsons

**Problem:** A pit display has a basic `Light`, and a `StatusLight` that is a kind of `Light` with one extra ability: `flash()`, which turns the light on (using the inherited `turnOn()` method) and then prints `Flashing`. Given this main class and superclass, which are already written:

```java
public class PitLights
{
    public static void main(String[] args)
    {
        StatusLight ring = new StatusLight();
        ring.flash();
    }
}

class Light
{
    public void turnOn()
    {
        System.out.println("Light on");
    }
}
```

Reorder the fragments below into the `StatusLight` class that goes right after `Light`, so the program prints `Light on` and then `Flashing`:

- a. `        turnOn();`
- b. `class StatusLight extends Light`
- c. `    }`
- d. `    public void flash()`
- e. `}`
- f. `        System.out.println("Flashing");`
- g. `{`
- h. `    {`

**Answer:** b, g, d, h, a, f, c, e

```java
public class PitLights
{
    public static void main(String[] args)
    {
        StatusLight ring = new StatusLight();
        ring.flash();
    }
}

class Light
{
    public void turnOn()
    {
        System.out.println("Light on");
    }
}

class StatusLight extends Light
{
    public void flash()
    {
        turnOn();
        System.out.println("Flashing");
    }
}
```

**Why this order:** The class line (`b`) comes first — `extends Light` is what makes `StatusLight` a subclass, and it belongs in the class declaration itself, before the class's opening brace (`g`). The new method's signature (`d`) and its opening brace (`h`) come next. Inside `flash()`, `turnOn()` (`a`) must come before the `println` (`f`), since the program has to print `Light on` before `Flashing`. `StatusLight` never defines `turnOn()` itself — it can call it only because it inherited it from `Light`. Then the braces close in reverse order: the method's body (`c`), then the class's body (`e`).


## Coding

**Mode:** full-program

**Problem:** `RobotPart` (below, already written, and not to be changed) is the course's
superclass for robot mechanisms. Write two classes:

- `Intake`, a **subclass** of `RobotPart` (an intake *is a* robot part). It holds a count of game
  pieces, starting at `0`. `addPiece()` adds one piece, but an intake holds at most `MAX_PIECES = 2`;
  once it is full, `addPiece()` does nothing. `getPieceCount()` returns the count. The constructor
  takes the intake's name and hands it to `RobotPart`.
- `Robot`, which **has an** `Intake` (a field, not a superclass). Its constructor takes the intake's
  name and builds the `Intake`; `getIntake()` returns it.

`Intake` should *not* write its own `log` or `stop`: it inherits them from `RobotPart`. The fixed
`main` reads an intake name and a number of pieces to pick up, then logs how many the intake ended
up holding and stops it. For the input `Front 3`:

```text
[Front] holding 2
[Front] stopped
```

**Solution:**

```java
import java.util.*;

public class Main
{
    // Don't change main
    public static void main(String[] args)
    {
        Scanner in = new Scanner(System.in);
        Robot robot = new Robot(in.next());
        int pickups = in.nextInt();
        for (int i = 0; i < pickups; i++)
        {
            robot.getIntake().addPiece();
        }
        robot.getIntake().log("holding " + robot.getIntake().getPieceCount());
        robot.getIntake().stop();
    }
}

// Don't change RobotPart
class RobotPart
{
    private String name;

    public RobotPart(String name) { this.name = name; }
    public String getName() { return name; }
    public void log(String msg) { System.out.println("[" + name + "] " + msg); }
    public void stop() { log("stopped"); }
}

class Intake extends RobotPart
{
    private static final int MAX_PIECES = 2;
    private int pieceCount;

    public Intake(String name)
    {
        super(name);
        pieceCount = 0;
    }

    public void addPiece()
    {
        if (pieceCount < MAX_PIECES)
        {
            pieceCount++;
        }
    }

    public int getPieceCount() { return pieceCount; }
}

class Robot
{
    private Intake intake;

    public Robot(String intakeName)
    {
        intake = new Intake(intakeName);
    }

    public Intake getIntake() { return intake; }
}
```

**Why:** `Intake extends RobotPart` is the is-a relationship, so `log` and `stop` come for free and
`main` can call them on an `Intake`. The constructor passes the name up with `super(name)`
(Lesson 17.2 explains why). `Robot` is has-a: it holds an `Intake` in a field and builds it,
and is *not* a subclass of anything. The cap lives in `addPiece()`; forgetting it is caught by the
`Top 9` scenario, which expects `2` pieces rather than `9`.
