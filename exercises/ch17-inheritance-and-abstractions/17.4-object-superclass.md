# Object Superclass — Exercises

## Multiple Choice

**Question:** Given these two classes:

```java
class Pump
{
    private int port;

    public Pump(int port)
    {
        this.port = port;
    }

    @Override
    public String toString()
    {
        return "Pump " + port;
    }
}

class VacuumPump extends Pump
{
    public VacuumPump(int port)
    {
        super(port);
    }

    @Override
    public String toString()
    {
        return super.toString() + " [vacuum]";
    }
}
```

What does `System.out.println(new VacuumPump(2));` print?

**Options:**

- A. `Pump 2 [vacuum]`
- B. `Pump 2`
- C. ` [vacuum]`
- D. Something like `VacuumPump@3b07d329`

**Answer:** A

**Why:** `println` calls the object's `toString()` automatically. The object is a `VacuumPump`, so `VacuumPump`'s own `toString()` runs. Its first step, `super.toString()`, runs `Pump`'s version, which returns `"Pump 2"`. `VacuumPump`'s version then appends `" [vacuum]"` to that.

- B is wrong — that's what a plain `Pump` would print. `VacuumPump` overrides `toString()`, so its own version runs, and that version adds `" [vacuum]"`.
- C is wrong — `super.toString()` isn't skipped or empty. It calls `Pump`'s `toString()`, which returns `"Pump 2"`, and that becomes the start of the result.
- D is wrong — that's `Object`'s default `toString()`, which only runs when no class in the chain overrides it. Here both `Pump` and `VacuumPump` do.

## Micro-Parsons

**Problem:** Two `FieldTag` objects should count as equal when they have the same `id`. Given this program, with the `equals` method missing (its partner, `hashCode()`, is already written from the same `id` field, as Lesson 17.4 requires):

```java
public class TagCheck
{
    public static void main(String[] args)
    {
        FieldTag seen = new FieldTag(7);
        FieldTag expected = new FieldTag(7);
        System.out.println(seen == expected);
        System.out.println(seen.equals(expected));
    }
}

class FieldTag
{
    private int id;

    public FieldTag(int id)
    {
        this.id = id;
    }

    // equals method goes here

    @Override
    public int hashCode()
    {
        return id;
    }
}
```

Reorder the fragments below into the `equals` method, following the standard recipe (same-object check, `instanceof` check, cast, compare fields), so the program prints `false` and then `true`:

- a. `        FieldTag o = (FieldTag) other;`
- b. `    public boolean equals(Object other)`
- c. `    }`
- d. `        if (this == other) return true;`
- e. `        return this.id == o.id;`
- f. `    @Override`
- g. `        if (!(other instanceof FieldTag)) return false;`
- h. `    {`

**Answer:** f, b, h, d, g, a, e, c

**Interchangeable:** (d, g)

```java
public class TagCheck
{
    public static void main(String[] args)
    {
        FieldTag seen = new FieldTag(7);
        FieldTag expected = new FieldTag(7);
        System.out.println(seen == expected);
        System.out.println(seen.equals(expected));
    }
}

class FieldTag
{
    private int id;

    public FieldTag(int id)
    {
        this.id = id;
    }

    @Override
    public boolean equals(Object other)
    {
        if (this == other) return true;
        if (!(other instanceof FieldTag)) return false;
        FieldTag o = (FieldTag) other;
        return this.id == o.id;
    }

    @Override
    public int hashCode()
    {
        return id;
    }
}
```

**Why this order:** `@Override` (`f`) goes directly above the method it marks, the signature (`b`), and then comes the opening brace (`h`). The parameter type is `Object`, not `FieldTag`, which is what makes this an override of `Object`'s `equals` rather than a new overloaded method. The two early-exit checks (`d` and `g`) come next. They're interchangeable: each one returns early on its own, and swapping them never changes the result. The cast (`a`) must come *after* the `instanceof` check (`g`), because casting something that isn't a `FieldTag` would throw a `ClassCastException`. The comparison (`e`) needs the cast variable `o`, so it follows `a`. The method's closing brace (`c`) comes last. The program prints `false` because `seen` and `expected` are two separate objects, and `true` because their `id`s match.

**Solution:**

```java
import java.util.*;

public class Main
{
    // Don't change main
    public static void main(String[] args)
    {
        Scanner in = new Scanner(System.in);
        HashSet<CanDevice> devices = new HashSet<CanDevice>();
        int count = in.nextInt();
        for (int i = 0; i < count; i++)
        {
            devices.add(new CanDevice(in.nextInt(), in.next()));
        }
        CanDevice probe = new CanDevice(in.nextInt(), in.next());
        CanDevice other = new CanDevice(in.nextInt(), in.next());
        System.out.println(devices.size());
        System.out.println(devices.contains(probe));
        System.out.println(probe);
        System.out.println(probe.equals(other));
    }
}

class CanDevice
{
    private int id;
    private String name;

    public CanDevice(int id, String name)
    {
        this.id = id;
        this.name = name;
    }

    @Override
    public String toString()
    {
        return name + " [" + id + "]";
    }

    @Override
    public boolean equals(Object other)
    {
        if (this == other) return true;
        if (!(other instanceof CanDevice)) return false;
        CanDevice o = (CanDevice) other;
        return this.id == o.id && this.name.equals(o.name);
    }

    @Override
    public int hashCode()
    {
        return Objects.hash(id, name);
    }
}
```

**Why:** A `HashSet` first uses `hashCode()` to pick where to look, then `equals(Object)` to
confirm a match, so both have to agree and both have to use the same fields (`id` and `name`). If
`equals` is written without `hashCode`, two equal devices usually hash to different places and the
set keeps both, so `size()` comes out too large and `contains` can say `false` for a device that
is really there. Writing the parameter as `equals(CanDevice other)` is a different method
(overloading), which the set never calls; `@Override` turns that mistake into a compile error. The
`id` comparison uses `==` because `id` is a primitive `int`, but `name` is a `String` and needs
`.equals`.
