## Problem: Trace the Ramp

Below is a simplified version of a motor-ramping loop, run for exactly 4 iterations (imagine the scheduler calling it 4 times, 20ms apart). Without running it, write a trace table tracking `currentPower` and `iterationsAtTarget` after each line of the loop body, for all 4 iterations. Then check your table against the solution.

```java
double currentPower = 0.20;
double targetPower = 0.30;
double rampRate = 0.05;
int iterationsAtTarget = 0;

// --- one iteration of the loop, run 4 times total ---
currentPower += rampRate;
if (currentPower > targetPower) {
    currentPower = targetPower;
}
if (currentPower == targetPower) {
    iterationsAtTarget++;
}
```

## Hints

- Process one iteration completely (all 3 lines) before moving to the next — don't skip ahead.
- The clamp (`if (currentPower > targetPower)`) only fires once `currentPower` has actually overshot — check the comparison carefully each time, don't assume.
- Once `currentPower` reaches `targetPower` exactly, does it ever change again on later iterations? Trace it and see.

## Solution

| Iteration | `currentPower` after `+=` | Clamped? | `currentPower` final | `iterationsAtTarget` |
|---|---|---|---|---|
| 1 | 0.25 | no (0.25 ≤ 0.30) | 0.25 | 0 |
| 2 | 0.30 | no (0.30 is not `>` 0.30) | 0.30 | 1 (0.30 == 0.30) |
| 3 | 0.35 | yes → 0.30 | 0.30 | 2 |
| 4 | 0.35 | yes → 0.30 | 0.30 | 3 |

Final values after 4 iterations: `currentPower = 0.30`, `iterationsAtTarget = 3`.

The subtle part worth noticing: on iteration 2, `currentPower` reaches exactly `0.30` *without ever triggering the clamp* — the clamp's `>` comparison only fires on iteration 3, once floating-point addition has pushed it slightly past. This is exactly why the clamp exists as its own separate check, rather than assuming the ramp will "naturally" stop at the target.
