# Abstraction and Program Design — Exercises

## Multiple Choice

**Question:** A robot's code calls `arm.getAngleDegrees()` from twelve different places. A teammate rewrites the *inside* of `getAngleDegrees()` to use a cleaner calculation. Its signature (`public double getAngleDegrees()`) is unchanged, and it returns exactly the same value as before for every arm position. What has to change in those twelve calling lines?

**Options:**

- A. Nothing — the callers keep working exactly as written
- B. Each call has to be rewritten to use the new calculation directly
- C. Each call now needs an extra argument telling the method which calculation to use
- D. Every call has to be moved into the same class as `getAngleDegrees()`

**Answer:** A

**Why:** This is procedural abstraction's payoff: callers depend only on *what* a method does — its name, parameters, return type, and observable behavior — not on *how* it does it. Since all of those stayed the same, the internals were free to change without breaking any caller.

- B is wrong — the whole point of naming a process as a method is that callers never have to contain the calculation themselves; they just call it by name.
- C is wrong — the signature didn't change, so the parameter list is still empty; adding an argument to a call would no longer match the method and wouldn't compile.
- D is wrong — where a caller lives has nothing to do with this change; a method call keeps working from wherever it could be reached before, since nothing about its signature or visibility changed.

## Micro-Parsons

**Problem:** These lines, once correctly ordered, form a complete program with one named method that turns a motor's RPM into the gearbox output's RPM (for an 8:1 reduction). `main` calls that method twice — first for 4000 motor RPM, then for 6000 — so one method handles both inputs instead of needing a separate calculation for each.

Reorder the fragments below into a working program:

- a. `    public static double outputRpm(double motorRpm)`
- b. `    }`
- c. `        System.out.println("At 6000: " + outputRpm(6000.0));`
- d. `public class GearboxMath`
- e. `        return motorRpm / 8.0;`
- f. `    {`
- g. `}`
- h. `        System.out.println("At 4000: " + outputRpm(4000.0));`
- i. `    public static void main(String[] args)`
- j. `{`
- k. `    {`
- l. `    }`

**Answer:** d, j, a, f, e, b, i, k, h, c, l, g

```java
public class GearboxMath
{
    public static double outputRpm(double motorRpm)
    {
        return motorRpm / 8.0;
    }

    public static void main(String[] args)
    {
        System.out.println("At 4000: " + outputRpm(4000.0));
        System.out.println("At 6000: " + outputRpm(6000.0));
    }
}
```

**Why this order:** The class line (`d`) and its opening brace (`j`) come first. The named method's signature (`a`) comes next with its own opening brace (`f`), then its one statement (`e`) — the calculation lives here, in exactly one place — and its closing brace (`b`). `main` (`i`) and its opening brace (`k`) follow. Inside `main`, the 4000 line (`h`) goes before the 6000 line (`c`) because the Problem asks for that order; both lines only use the method by name, `outputRpm(...)`, without repeating how it works, and the `motorRpm` parameter is what lets that one method handle both inputs. Then `main`'s body closes (`l`), and finally the class's body (`g`). Note that `f` and `k` are textually identical (`    {`), as are `b` and `l` (`    }`) — only the surrounding context tells them apart. Java also doesn't require `outputRpm` to be declared before `main`; the order here follows the Problem's framing (define the named method, then use it).
