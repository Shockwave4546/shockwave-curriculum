# Impact of Program Design — Exercises

## Multiple Choice

**Question:** A teammate finishes a new auto-align routine for the robot's shooter. It compiles cleanly, and it lined up correctly the one time they ran it on the practice field. Which next step does the most to show the routine is actually *reliable*?

**Options:**

- A. Compile it a second time to double-check there are no errors
- B. Run it again under the conditions it will really face — a partly drained battery, the camera unplugged mid-run, a game piece jammed in the shooter — and check what it does in each
- C. Nothing more is needed — compiling cleanly and working once on the practice field together prove it's reliable
- D. Add detailed comments explaining how each part of the routine works

**Answer:** B

**Why:** System reliability means the program performs its intended task correctly *under stated conditions*, without failure — and the only way to know that is to actually test it across the realistic range of conditions it'll meet in a match, including the edge cases where things go wrong.

- A is wrong — compiling only confirms the code is syntactically valid, and recompiling unchanged code just repeats the same check. It says nothing about how the routine behaves.
- C is wrong — "it compiled" is not the same as "it's reliable," and one successful run under ideal conditions says nothing about a low battery, a lost camera, or a jam.
- D is wrong — comments can make code easier to read and maintain, but they don't change or test its behavior, so they can't show it works under real conditions.
