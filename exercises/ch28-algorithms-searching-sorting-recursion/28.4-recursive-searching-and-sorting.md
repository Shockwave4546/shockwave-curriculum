# Recursive Searching and Sorting — Exercises

## Multiple Choice

**Question:** The lesson's `mergeSort` is called on an array of intake current spikes (in amps). `mergeSortHelper` sorts the left half, then the right half, then merges them. What does the array look like right **before** the final `merge` call, the one that combines indexes 0-1 with indexes 2-3?

```java
int[] currentSpikes = {9, 4, 7, 1};
mergeSort(currentSpikes);
```

**Options:**

- A. `{9, 4, 7, 1}`
- B. `{4, 9, 7, 1}`
- C. `{4, 9, 1, 7}`
- D. `{1, 4, 7, 9}`

**Answer:** C

**Why:** Before the final merge can run, `mergeSortHelper` has already finished both of its recursive calls. The left-half call split `{9, 4}` into `{9}` and `{4}` and merged them into `{4, 9}`. Then the right-half call split `{7, 1}` into `{7}` and `{1}` and merged them into `{1, 7}`. The array is sorted in place, so it now reads `{4, 9, 1, 7}`: each half is sorted on its own, but the whole array isn't sorted yet. The final merge's job is to combine them into `{1, 4, 7, 9}`.

- A is wrong. That's the array before any work at all. The merges of the single-element halves happen during the recursive calls, before the final merge.
- B is wrong. That's the state after only the left half is sorted. `mergeSortHelper` makes the right-half call *before* it calls `merge`, so `{7, 1}` is already sorted into `{1, 7}` by the time the final merge starts.
- D is wrong. That's the finished result, which only exists *after* the final merge. If the array were already fully sorted, the final merge would have nothing to do.

## Micro-Parsons

**Problem:** Given an `ElevatorPresets` class whose `main` method creates the sorted array `int[] presetHeights = {20, 45, 80, 110, 150};` and prints `findPreset(presetHeights, 0, presetHeights.length - 1, 110)`, reorder the fragments below into the complete recursive binary search method `findPreset`. It must return the index of `target`, or `-1` if `target` isn't in the range `start`..`end`. The single-statement `if`/`else` branches are written without braces here, like the lesson's `mergeSortHelper` writes `if (from >= to) return;`.

Reorder the fragments below into a working method:

- a. `    int middle = (start + end) / 2;`
- b. `    else return findPreset(presets, middle + 1, end, target);`
- c. `public static int findPreset(int[] presets, int start, int end, int target)`
- d. `    if (target == presets[middle]) return middle;`
- e. `}`
- f. `    if (end < start) return -1;`
- g. `    else if (target < presets[middle]) return findPreset(presets, start, middle - 1, target);`
- h. `{`

**Answer:** c, h, f, a, d, g, b, e

**Interchangeable:** (f, a)

```java
public class ElevatorPresets
{
    public static int findPreset(int[] presets, int start, int end, int target)
    {
        if (end < start) return -1;
        int middle = (start + end) / 2;
        if (target == presets[middle]) return middle;
        else if (target < presets[middle]) return findPreset(presets, start, middle - 1, target);
        else return findPreset(presets, middle + 1, end, target);
    }

    public static void main(String[] args)
    {
        int[] presetHeights = {20, 45, 80, 110, 150};
        System.out.println(findPreset(presetHeights, 0, presetHeights.length - 1, 110));
    }
}
```

**Why this order:** The signature (`c`) and opening brace (`h`) come first. The empty-range base case (`f`) and the `middle` calculation (`a`) come next, in either order. Computing `middle` is only arithmetic and never reads the array, so doing it before or after the `end < start` check doesn't change the result. The lesson checks the base case first, which is why the Answer lists `f` first. Both of them have to come before the match check (`d`), for two reasons. `d` reads `presets[middle]`, so `middle` has to exist already. And on an empty range (for example, a search of an empty array, where `start` is `0` and `end` is `-1`), reading `presets[middle]` before returning `-1` would go outside the array. The match check (`d`) is the second base case. The two recursive calls follow as the `else if` (`g`) and then the `else` (`b`), since an `else` only attaches to an `if`/`else if` directly above it. Each call passes a range that leaves out `middle`, so the range always shrinks toward one of the two base cases. The method's brace (`e`) closes last. The class and `main` are the given scaffold. The finished program prints `3`, since `110` is at index 3.

## Coding

**Mode:** harness

**Problem:** Write a **recursive** binary search over a `String[]` of subsystem names that is
already sorted alphabetically (compare with `compareTo`, not `<`). The search looks only at the
indices from `start` to `end`, inclusive. Return the index where `target` is found, or `-1` if it
isn't in that range. Names are unique. A call with `end < start` means the range is empty.

Examples (with `names` = `{"Climber", "Drive", "Intake", "Shooter"}` and the whole range `0, 3`):

- `recursiveSearch(names, 0, 3, "Intake")` returns `2`
- `recursiveSearch(names, 0, 3, "Drive")` returns `1`
- `recursiveSearch(names, 0, 3, "Zebra")` returns `-1`

**Signature:** `public static int recursiveSearch(String[] sortedNames, int start, int end, String target)`

**Starter:**

```java
public class Solution
{
    public static int recursiveSearch(String[] sortedNames, int start, int end, String target)
    {
        // TODO: two base cases, then search the correct half recursively
    }
}
```

**Tests:**

| Visible | Arguments | Expected |
|---|---|---|
| yes | `new String[] {"Climber", "Drive", "Intake", "Shooter"}, 0, 3, "Intake"` | `2` |
| yes | `new String[] {"Climber", "Drive", "Intake", "Shooter"}, 0, 3, "Drive"` | `1` |
| yes | `new String[] {"Climber", "Drive", "Intake", "Shooter"}, 0, 3, "Zebra"` | `-1` |
| no | `new String[] {"Climber", "Drive", "Intake", "Shooter"}, 0, 3, new String("Drive")` | `1` |
| no | `new String[] {"Climber", "Drive", "Intake", "Shooter"}, 0, 3, "Climber"` | `0` |
| no | `new String[] {"Climber", "Drive", "Intake", "Shooter"}, 0, 3, "Shooter"` | `3` |
| no | `new String[] {"Climber", "Drive", "Intake", "Shooter"}, 0, 3, "Elevator"` | `-1` |
| no | `new String[] {"Climber", "Drive", "Intake", "Shooter"}, 0, 3, "Aardvark"` | `-1` |
| no | `new String[] {}, 0, -1, "Drive"` | `-1` |

**Solution:**

```java
public class Solution
{
    public static int recursiveSearch(String[] sortedNames, int start, int end, String target)
    {
        if (end < start)
        {
            return -1;
        }
        int middle = (start + end) / 2;
        int order = target.compareTo(sortedNames[middle]);
        if (order == 0)
        {
            return middle;
        }
        else if (order < 0)
        {
            return recursiveSearch(sortedNames, start, middle - 1, target);
        }
        else
        {
            return recursiveSearch(sortedNames, middle + 1, end, target);
        }
    }
}
```

**Why:** The shrinking range `start..end` does the job the `while` loop's condition did in the
iterative version. There are two base cases: an empty range (`end < start`) means the target isn't
there, and a match at `middle` returns its index. `compareTo` returns zero for equal text, negative
if `target` sorts before the middle name (search the left half, `middle - 1`), and positive if after
(search the right half, `middle + 1`). Comparing the names with `==` instead of `compareTo` happens to
work for string literals but fails for a `String` that was built separately, as the
`new String("Drive")` test shows. Leaving out the `end < start` base case makes a search for a missing
name recurse until it crashes.
