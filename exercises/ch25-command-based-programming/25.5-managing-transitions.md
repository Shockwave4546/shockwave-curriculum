# Managing Transitions — Exercises

## Multiple Choice

**Question:** An intake's state machine runs this arrow-form `switch` as the body of its default command. It has no `case` for `SCORING`:

```java
switch (currentState)
{
    case IDLE -> { /* ... */ }
    case INTAKING -> { /* ... */ }
    case HOLDING -> { /* ... */ }
}
```

Somehow `currentState` becomes `SCORING`. What happens the next time the `switch` runs?

**Options:**

- A. The `switch` throws a runtime exception, because `SCORING` isn't handled.
- B. The `switch` does nothing that loop — no case matches, so no state action runs and no guard is checked — and the machine stays in `SCORING` forever.
- C. The code doesn't compile, because the `switch` doesn't cover every constant of the enum.
- D. Java automatically runs the `IDLE` case as a fallback.

**Answer:** B

**Why:** A `switch` *statement* (unlike a `switch` expression) doesn't have to be exhaustive — `default` is optional, and leaving a case out just means "do nothing" is a real outcome for that value (Lesson 5.12). With no case matching `SCORING`, the switch body simply runs nothing that loop. Since nothing else assigns `currentState`, the machine sits in `SCORING` for the rest of the match — exactly the "state with no way out" pitfall Lesson 25.4 warns about.

- A is wrong — an unmatched value in a `switch` statement is not an error; it just means no case runs. (Only a `switch` *expression* must always produce a value, and even that's a compile-time requirement, not a runtime exception.)
- C is wrong — exhaustiveness is required for `switch` expressions, not `switch` statements; that's exactly why this compiles despite missing a state.
- D is wrong — there's no such fallback; only an explicit `default` case would run, and this `switch` doesn't have one.

## Micro-Parsons

**Problem:** This program is a plain-Java stand-in for a shooter's state machine, using the arrow-form `switch` from Lesson 25.5: `main` calls `update()` three times, standing in for three scheduler loops, and raises `flywheelRpm` to 3200 before the second call. While `SPINNING_UP`, it should print `Spinning up` and move to `READY` once `flywheelRpm` is at least 3000; while `READY`, it should print `Ready to fire`.

*Note on file order:* like the enum in Lesson 25.4's exercise, this file declares `ShooterState` before the class that uses it — fine on Java 25, but Java 17's single-file launcher would need the class with `main` first.

Given this enum, class, fields, and `main` method:

```java
enum ShooterState
{
    SPINNING_UP, READY
}

public class ShooterStateMachine
{
    private ShooterState currentState = ShooterState.SPINNING_UP;
    private double flywheelRpm = 0.0;

    public void update()
    {
        // your fragments go here
    }

    public static void main(String[] args)
    {
        ShooterStateMachine shooter = new ShooterStateMachine();
        shooter.update();
        shooter.flywheelRpm = 3200.0;
        shooter.update();
        shooter.update();
    }
}
```

Reorder the fragments below into the body of `update()`:

- a. `        switch (currentState)`
- b. `        {`
- c. `            case SPINNING_UP ->`
- d. `            {`
- e. `                System.out.println("Spinning up");`
- f. `                if (flywheelRpm >= 3000)`
- g. `                {`
- h. `                    currentState = ShooterState.READY;`
- i. `                }`
- j. `            }`
- k. `            case READY -> System.out.println("Ready to fire");`
- l. `        }`

**Answer:** a, b, c, d, e, f, g, h, i, j, k, l

```java
enum ShooterState
{
    SPINNING_UP, READY
}

public class ShooterStateMachine
{
    private ShooterState currentState = ShooterState.SPINNING_UP;
    private double flywheelRpm = 0.0;

    public void update()
    {
        switch (currentState)
        {
            case SPINNING_UP ->
            {
                System.out.println("Spinning up");
                if (flywheelRpm >= 3000)
                {
                    currentState = ShooterState.READY;
                }
            }
            case READY -> System.out.println("Ready to fire");
        }
    }

    public static void main(String[] args)
    {
        ShooterStateMachine shooter = new ShooterStateMachine();
        shooter.update();
        shooter.flywheelRpm = 3200.0;
        shooter.update();
        shooter.update();
    }
}
```

**Why this order:** The `switch` header (`a`) and its brace (`b`) wrap everything. `SPINNING_UP`'s arrow case (`c`) opens a block (`d`) — it needs one because it runs two statements: the state action (`e`) and then the guard, `if (flywheelRpm >= 3000)` (`f`), whose own block (`g`, `h`, `i`) makes the transition. `SPINNING_UP`'s block closes (`j`). `READY` (`k`) needs no braces — one statement follows its arrow directly, ending in its own semicolon, which is why arrow-form cases don't need `break;`. The `switch`'s brace closes last (`l`).

The program prints `Spinning up`, `Spinning up`, `Ready to fire`: on the second call the RPM check passes and the state becomes `READY`, but `Spinning up` was already printed earlier in that same call, before the check ran — so `Ready to fire` only shows up on the third call.
