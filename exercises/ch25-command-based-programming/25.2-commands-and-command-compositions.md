# Commands & Command Compositions — Exercises

## Multiple Choice

**Question:** Roughly how long after it's scheduled does this composition finish?

```java
Command routine = Commands.waitSeconds(2.0)
    .andThen(Commands.parallel(Commands.waitSeconds(1.0), Commands.waitSeconds(3.0)));
```

**Options:**

- A. About 3 seconds
- B. About 5 seconds
- C. About 6 seconds
- D. About 1 second

**Answer:** B

**Why:** `andThen` is sequential: the 2-second wait runs first, and only when it finishes does the parallel group start. A parallel group finishes once *all* of its commands finish, so it lasts as long as its longest member — 3 seconds. Total: 2 + 3 = 5 seconds.

- A is wrong — 2 + 1 = 3 treats the parallel group like a race, which ends when the *first* member finishes. `parallel` waits for the last one.
- C is wrong — 2 + 1 + 3 = 6 runs everything back to back, but the 1-second and 3-second waits run at the same time, not one after the other.
- D is wrong — that would only happen if all three waits raced each other from the start; `andThen` makes the parallel group wait until the 2-second wait is done.

## Micro-Parsons

**Problem:** These lines, once correctly ordered, form a complete `Command` subclass named `ExtendHook`. It receives a `ClimberSubsystem` through its constructor, declares it as a requirement, calls `climber.extendHook()` once when the command starts, and calls `climber.holdPosition()` once when the command ends. Declare the constructor first, then `initialize()`, then `end(...)` — the order the scheduler first calls them.

Reorder the fragments below into a working class:

- a. `    public void initialize() { climber.extendHook(); }`
- b. `public class ExtendHook extends Command`
- c. `        addRequirements(climber);`
- d. `    @Override`
- e. `    private final ClimberSubsystem climber;`
- f. `}`
- g. `    public ExtendHook(ClimberSubsystem subsystem)`
- h. `    public void end(boolean interrupted) { climber.holdPosition(); }`
- i. `    {`
- j. `        climber = subsystem;`
- k. `{`
- l. `    }`
- m. `    @Override`

**Answer:** b, k, e, g, i, j, c, l, d, a, m, h, f

**Interchangeable:** (d, m)

```java
public class ExtendHook extends Command
{
    private final ClimberSubsystem climber;

    public ExtendHook(ClimberSubsystem subsystem)
    {
        climber = subsystem;
        addRequirements(climber);
    }

    @Override
    public void initialize() { climber.extendHook(); }

    @Override
    public void end(boolean interrupted) { climber.holdPosition(); }
}
```

**Why this order:** The class header (`b`) and its brace (`k`) come first, then the field (`e`) that will hold the subsystem. The constructor (`g`, `i`) must store the injected subsystem in the field (`j`) *before* `addRequirements(climber)` (`c`) reads that field — in the other order, the class won't even compile, because Java refuses to read a `final` field before the constructor has assigned it. The constructor's brace closes (`l`). Each lifecycle method is marked with `@Override` directly above it (`d` before `a`, `m` before `h`), since each one replaces a do-nothing default from `Command`. The class's brace closes last (`f`). `isFinished()` is left out on purpose: its default returns `false`, so this command keeps running (with nothing to do in `execute()`) until something interrupts it — at which point `end(true)` calls `holdPosition()`.

`d` and `m` are the same text (`    @Override`), so either one works in either spot.
