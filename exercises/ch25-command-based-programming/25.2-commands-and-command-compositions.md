# Commands & Command Compositions — Exercises

## Multiple Choice

**Question:** Roughly how long after it's scheduled does this composition finish?

```java
Command routine = Command.waitFor(Seconds.of(2)).named("Wait 2 s")
    .andThen(Command.parallel(
        Command.waitFor(Seconds.of(1)).named("Wait 1 s"),
        Command.waitFor(Seconds.of(3)).named("Wait 3 s")).named("Both Waits"))
    .named("Routine");
```

**Options:**

- A. About 3 seconds
- B. About 5 seconds
- C. About 6 seconds
- D. About 1 second

**Answer:** B

**Why:** `andThen` is sequential: the 2-second wait runs first, and only when it finishes does the parallel group start. A parallel group finishes once *all* of its commands finish, so it lasts as long as its longest member — 3 seconds. Total: 2 + 3 = 5 seconds.

- A is wrong — 2 + 1 = 3 treats the parallel group like a race, which ends when the *first* member finishes. `parallel` waits for the last one.
- C is wrong — 2 + 1 + 3 = 6 runs everything back to back, but the 1-second and 3-second waits run at the same time, not one after the other.
- D is wrong — that would only happen if all three waits raced each other from the start; `andThen` makes the parallel group wait until the 2-second wait is done.

## Micro-Parsons

**Problem:** A `Climber` class that `implements Mechanism` has three methods of its own: `extendHook()` starts the hook motor, `hookAtTop()` returns `true` once the hook is fully extended, and `holdPosition()` holds the hook where it is. Write the factory method `extendHookCommand()`: it extends the hook once when the command starts, pauses once per loop until the hook is at the top, and holds position however the command ends. Its name is `"Extend Hook"`.

Given this class:

```java
public class Climber implements Mechanism
{
    // your fragments go here
}
```

Reorder the fragments below into the `extendHookCommand()` method:

- a. `                coroutine.yield();`
- b. `    public Command extendHookCommand()`
- c. `        }).whenExited(() -> holdPosition()).named("Extend Hook");`
- d. `            extendHook();`
- e. `    {`
- f. `            while (!hookAtTop())`
- g. `        return run(coroutine -> {`
- h. `    }`
- i. `            {`
- j. `            }`

**Answer:** b, e, g, d, f, i, a, j, c, h

```java
public class Climber implements Mechanism
{
    public Command extendHookCommand()
    {
        return run(coroutine -> {
            extendHook();
            while (!hookAtTop())
            {
                coroutine.yield();
            }
        }).whenExited(() -> holdPosition()).named("Extend Hook");
    }
}
```

**Why this order:** The method's signature (`b`) and brace (`e`) come first. `return run(coroutine -> {` (`g`) starts building a command that requires this climber, with one body. Inside the body, `extendHook()` (`d`) comes before the loop, so it runs exactly once, when the command starts. The loop (`f`, `i`, `a`, `j`) keeps checking `hookAtTop()`, and its body is `coroutine.yield()` — pausing until the next scheduler loop. Without that yield, the loop would never give control back and the whole robot would hang. Then `})` closes the body and the `run(...)` call on the same fragment (`c`), which adds `whenExited(...)` — so `holdPosition()` runs whether the hook reaches the top or the command is canceled early — and finishes with `.named("Extend Hook")`, which turns the builder into a `Command`. The method's brace closes last (`h`). No `addRequirements(...)` appears anywhere: building the command with the climber's own `run(...)` makes it require the climber automatically.

## Coding

**Mode:** full-program

**Problem:** An `Elevator` (below, partly written) is a Commands v3 mechanism. `atTop()` reads the top limit
switch (here a flag that the fixed `main` flips). Write two pieces:

- `Elevator.raiseCommand()`: a command that **requires the elevator**, pauses once per loop (with
  `coroutine.yield()`) **until `atTop()` is `true`**, and is named `"Raise Elevator"`.
- `Autos.raiseThenWait(elevator, label)`: a **sequence** that runs the raise command, then a
  `Command.waitFor(...)` pause of **2 seconds** named `label`. Finish the sequence with
  `.withAutomaticName()`, so its name is built from its members.

The fixed `main` reads a label and a number of loops, builds both commands, and prints what it can
tell about them. Then it **runs the real scheduler** (on a fake clock): first the raise command,
with the top switch tripping after that many loops, then the whole routine over simulated seconds.
For the input below:

```text
Lift And Hold
2
```

the output is:

```text

Raise Elevator -> Lift And Hold | requires elevator: true
loop 1: raise running = true
loop 2: raise running = true
loop 3: raise running = false
loop 4: raise running = false
routine running = true
routine running = true
routine running = false
routine running = false
```

**Starter:**

import java.util.*;
import org.wpilib.command3.Command;
import org.wpilib.command3.Mechanism;
import org.wpilib.command3.Scheduler;
import org.wpilib.command3.TestSupport;
import static org.wpilib.units.Units.Seconds;

public class Main
{
    // Don't change main
    public static void main(String[] args)
    {
        TestSupport.init(); // a fake robot clock and opmode, so the scheduler can run without a robot
        Scanner in = new Scanner(System.in);
        String label = in.nextLine();
        int loopsUntilTop = in.nextInt();

        Elevator elevator = new Elevator();
        Command raise = elevator.raiseCommand();
        Command routine = Autos.raiseThenWait(elevator, label);
        System.out.println(raise.name() + " | requires elevator: " + raise.requires(elevator));
        System.out.println(routine.name() + " | requires elevator: " + routine.requires(elevator));

        // Run the raise command: the top switch trips after loopsUntilTop loops.
        Scheduler scheduler = Scheduler.getDefault();
        scheduler.schedule(raise);
        for (int loop = 1; loop <= 4; loop++)
        {
            elevator.setAtTop(loop > loopsUntilTop);
            scheduler.run();
            System.out.println("loop " + loop + ": raise running = " + scheduler.isRunning(raise));
        }

        // Run the whole routine on a fake clock. The elevator is already at the top.
        elevator.setAtTop(true);
        scheduler.schedule(routine);
        for (double step : new double[] { 0.0, 1.0, 1.0, 1.0 })
        {
            TestSupport.advance(step);
            scheduler.run();
            System.out.println("routine running = " + scheduler.isRunning(routine));
        }
    }
}

**Solution:**

```java
import java.util.*;
import org.wpilib.command3.Command;
import org.wpilib.command3.Mechanism;
import org.wpilib.command3.Scheduler;
import org.wpilib.command3.TestSupport;
import static org.wpilib.units.Units.Seconds;

public class Main
{
    // Don't change main
    public static void main(String[] args)
    {
        TestSupport.init(); // a fake robot clock and opmode, so the scheduler can run without a robot
        Scanner in = new Scanner(System.in);
        String label = in.nextLine();
        int loopsUntilTop = in.nextInt();

        Elevator elevator = new Elevator();
        Command raise = elevator.raiseCommand();
        Command routine = Autos.raiseThenWait(elevator, label);
        System.out.println(raise.name() + " | requires elevator: " + raise.requires(elevator));
        System.out.println(routine.name() + " | requires elevator: " + routine.requires(elevator));

        // Run the raise command: the top switch trips after loopsUntilTop loops.
        Scheduler scheduler = Scheduler.getDefault();
        scheduler.schedule(raise);
        for (int loop = 1; loop <= 4; loop++)
        {
            elevator.setAtTop(loop > loopsUntilTop);
            scheduler.run();
            System.out.println("loop " + loop + ": raise running = " + scheduler.isRunning(raise));
        }

        // Run the whole routine on a fake clock. The elevator is already at the top.
        elevator.setAtTop(true);
        scheduler.schedule(routine);
        for (double step : new double[] { 0.0, 1.0, 1.0, 1.0 })
        {
            TestSupport.advance(step);
            scheduler.run();
            System.out.println("routine running = " + scheduler.isRunning(routine));
        }
    }
}

class Elevator implements Mechanism
{
    private boolean atTop = false;

    public boolean atTop()
    {
        return atTop;
    }

    public void setAtTop(boolean atTop)
    {
        this.atTop = atTop;
    }

    public Command raiseCommand()
    {
        return run(coroutine -> {
            while (!atTop())
            {
                coroutine.yield();
            }
        }).named("Raise Elevator");
    }
}

class Autos
{
    public static Command raiseThenWait(Elevator elevator, String label)
    {
        return Command.sequence(
            elevator.raiseCommand(),
            Command.waitFor(Seconds.of(2)).named(label)
        ).withAutomaticName();
    }
}
```

**Why:** `elevator.run(...)` starts a command that requires `elevator` automatically, and `.named(...)` is
what finishes it. The `while` loop calls `coroutine.yield()` each pass, so the command **stays
running** until the switch trips, which is exactly when the loop condition becomes false: with
`loopsUntilTop = 2`, loops 1 and 2 are still running, and it finishes on loop 3. Without the
`yield()`, the loop would never give control back to the scheduler. A built-in composition requires
every mechanism any member requires, so the sequence requires the elevator too.
`withAutomaticName()` builds the sequence's name from its members, joined by `->`, so the printed
name shows that it is a *sequence* (a parallel group would print `&`) and the order of the steps.
The routine's running line also shows the 2-second pause: it stays running through the first two
simulated seconds of waiting and is done once the 2 seconds are up.
