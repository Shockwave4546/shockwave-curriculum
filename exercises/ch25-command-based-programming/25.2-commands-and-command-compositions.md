# Commands & Command Compositions — Exercises

## Multiple Choice

**Question:** Roughly how long after it's scheduled does this composition finish?

```java
Command routine = Command.waitFor(Seconds.of(2)).named("Wait 2 s")
    .andThen(Command.parallel(
        Command.waitFor(Seconds.of(1)).named("Wait 1 s"),
        Command.waitFor(Seconds.of(3)).named("Wait 3 s")).named("Both Waits"))
    .named("Routine");
```

**Options:**

- A. About 3 seconds
- B. About 5 seconds
- C. About 6 seconds
- D. About 1 second

**Answer:** B

**Why:** `andThen` is sequential: the 2-second wait runs first, and only when it finishes does the parallel group start. A parallel group finishes once *all* of its commands finish, so it lasts as long as its longest member — 3 seconds. Total: 2 + 3 = 5 seconds.

- A is wrong — 2 + 1 = 3 treats the parallel group like a race, which ends when the *first* member finishes. `parallel` waits for the last one.
- C is wrong — 2 + 1 + 3 = 6 runs everything back to back, but the 1-second and 3-second waits run at the same time, not one after the other.
- D is wrong — that would only happen if all three waits raced each other from the start; `andThen` makes the parallel group wait until the 2-second wait is done.

## Micro-Parsons

**Problem:** A `Climber` class that `implements Mechanism` has three methods of its own: `extendHook()` starts the hook motor, `hookAtTop()` returns `true` once the hook is fully extended, and `holdPosition()` holds the hook where it is. Write the factory method `extendHookCommand()`: it extends the hook once when the command starts, pauses once per loop until the hook is at the top, and holds position however the command ends. Its name is `"Extend Hook"`.

Given this class:

```java
public class Climber implements Mechanism
{
    // your fragments go here
}
```

Reorder the fragments below into the `extendHookCommand()` method:

- a. `                coroutine.yield();`
- b. `    public Command extendHookCommand()`
- c. `        }).whenExited(() -> holdPosition()).named("Extend Hook");`
- d. `            extendHook();`
- e. `    {`
- f. `            while (!hookAtTop())`
- g. `        return run(coroutine -> {`
- h. `    }`
- i. `            {`
- j. `            }`

**Answer:** b, e, g, d, f, i, a, j, c, h

```java
public class Climber implements Mechanism
{
    public Command extendHookCommand()
    {
        return run(coroutine -> {
            extendHook();
            while (!hookAtTop())
            {
                coroutine.yield();
            }
        }).whenExited(() -> holdPosition()).named("Extend Hook");
    }
}
```

**Why this order:** The method's signature (`b`) and brace (`e`) come first. `return run(coroutine -> {` (`g`) starts building a command that requires this climber, with one body. Inside the body, `extendHook()` (`d`) comes before the loop, so it runs exactly once, when the command starts. The loop (`f`, `i`, `a`, `j`) keeps checking `hookAtTop()`, and its body is `coroutine.yield()` — pausing until the next scheduler loop. Without that yield, the loop would never give control back and the whole robot would hang. Then `})` closes the body and the `run(...)` call on the same fragment (`c`), which adds `whenExited(...)` — so `holdPosition()` runs whether the hook reaches the top or the command is canceled early — and finishes with `.named("Extend Hook")`, which turns the builder into a `Command`. The method's brace closes last (`h`). No `addRequirements(...)` appears anywhere: building the command with the climber's own `run(...)` makes it require the climber automatically.
