# What Is Command-Based Programming? — Exercises

## Multiple Choice

**Question:** In a command-based robot, a button binding and an autonomous routine both try to run a command that controls the climber at the same moment. What keeps the two commands from fighting over the climber's motor?

**Options:**

- A. Each command declares the climber as a requirement, and the CommandScheduler lets only one command control a given subsystem at a time.
- B. The `Trigger` that the button is bound to checks the condition every loop, so it always wins.
- C. Commands are recursively composable, so the two commands automatically merge into one.
- D. Nothing — the programmer has to add a `boolean` flag in `Robot.java` to track which command got there first.

**Answer:** A

**Why:** Requirements are what make resource management automatic: each command says which subsystem(s) it needs, and the scheduler guarantees that only one command controls a given subsystem at a time, so two pieces of code never drive the same motor at once.

- B is wrong — a `Trigger` only decides *when* its command gets scheduled; it has nothing to do with deciding which command controls a subsystem.
- C is wrong — composition is something you do on purpose, by combining commands yourself; the scheduler never merges two separately scheduled commands into one.
- D is wrong — hand-tracking state with a flag in `Robot.java` is exactly the imperative style command-based replaces; the scheduler's requirement system already handles this.

## Micro-Parsons

**Problem:** Here is the *imperative* way to react to a button: check it every loop yourself, and use a `pressed` flag so the action only fires once per press. In this program, `buttonReadings` stands in for the button's value on five loops in a row, and the robot should print `Deploy hook` only on a loop where the button has just gone from released to pressed.

Given this class, `main` method, and loop:

```java
public class HookDeploy
{
    public static void main(String[] args)
    {
        boolean[] buttonReadings = {false, true, true, false, true};
        boolean pressed = false;

        for (boolean buttonDown : buttonReadings)
        {
            // your fragments go here
        }
    }
}
```

Reorder the fragments below into the loop's body:

- a. `    pressed = false;`
- b. `if (buttonDown)`
- c. `        pressed = true;`
- d. `}`
- e. `    if (!pressed)`
- f. `{`
- g. `        System.out.println("Deploy hook");`
- h. `    }`
- i. `else`
- j. `    {`
- k. `{`
- l. `}`

**Answer:** b, f, e, j, g, c, h, d, i, k, a, l

**Interchangeable:** (g, c) (f, k) (d, l)

```java
public class HookDeploy
{
    public static void main(String[] args)
    {
        boolean[] buttonReadings = {false, true, true, false, true};
        boolean pressed = false;

        for (boolean buttonDown : buttonReadings)
        {
            if (buttonDown)
            {
                if (!pressed)
                {
                    System.out.println("Deploy hook");
                    pressed = true;
                }
            }
            else
            {
                pressed = false;
            }
        }
    }
}
```

**Why this order:** The outer `if (buttonDown)` (`b`) comes first, with its opening brace (`f`). Inside it, `if (!pressed)` (`e`) and its brace (`j`) guard the action so it only runs on the *first* loop the button is down; inside that, the action (`g`) runs and the flag is set (`c`) so the next loop with the button still down does nothing. The inner brace closes (`h`), then the outer `if`'s brace (`d`). The `else` (`i`), with its brace (`k`), must come right after the `if` block it pairs with; it resets the flag (`a`) once the button is released, so the *next* press can fire again, and its brace closes (`l`). The program prints `Deploy hook` twice — on the second reading and the fifth — never on the third, because the button was already held. This flag bookkeeping is exactly what a single declarative `onTrue` binding handles for you.

The interchangeable groups: `g` and `c` can go in either order, since printing doesn't read `pressed` and setting `pressed` doesn't affect the print. `f`/`k` are the same text (`{`), as are `d`/`l` (`}`), so either one of each pair works in either spot.
