# Structuring a Command-Based Robot Project — Exercises

## Multiple Choice

**Question:** A new "hand-off" command has to move the `Elevator` down and run the `Wrist` at the same time, so a game piece can pass from one mechanism to the other. Neither mechanism is more "in charge" of the hand-off than the other, and the command has no internal state of its own. Which is the best way to define it so it can be reused from a button binding and from autonomous?

**Options:**

- A. A static factory method, like `HandoffCommands.handoff(elevator, wrist)`, that takes both mechanisms as parameters
- B. An instance factory method on `Elevator`, like `elevator.handoffCommand()`
- C. A full class that `implements Command`, with its own fields for tracking state
- D. Make `elevator` and `wrist` `public static` fields in `Robot`, so the command can reach them from anywhere

**Answer:** A

**Why:** A command that coordinates *multiple* mechanisms doesn't naturally belong to any single one of them, which is exactly the case a static factory method is for. Passing both mechanisms in as parameters is dependency injection: the method gets exactly what it needs, explicitly.

- B is wrong — an instance factory on one mechanism is best for a command tied to *that one* mechanism; here the `Elevator` would need to reach the `Wrist`, which it has no business owning.
- C is wrong — a full `Command` class is for a command with genuine internal state or unusually complex logic; this one has neither, so a whole class is unnecessary.
- D is wrong — making mechanisms `public static` lets any code anywhere call their methods directly, bypassing the scheduler's resource-management guarantees; `Robot`'s mechanisms stay package-private and get passed explicitly to whatever needs them.

## Micro-Parsons

**Problem:** These lines, once correctly ordered, form a complete `Autos` class with one static factory method, `scoreAndBackUp`. It receives an `Elevator` and a `Drive` as parameters, and returns a named sequence that first raises the elevator, then releases the game piece, then drives backward for 2 seconds.

Reorder the fragments below into a working class:

- a. `            drive.driveBackwardCommand().withTimeout(Seconds.of(2))`
- b. `public class Autos`
- c. `    }`
- d. `        return Command.sequence(`
- e. `            elevator.raiseCommand(),`
- f. `{`
- g. `        ).named("Score And Back Up");`
- h. `    public static Command scoreAndBackUp(Elevator elevator, Drive drive)`
- i. `            elevator.releaseCommand(),`
- j. `    {`
- k. `}`

**Answer:** b, f, h, j, d, e, i, a, g, c, k

```java
public class Autos
{
    public static Command scoreAndBackUp(Elevator elevator, Drive drive)
    {
        return Command.sequence(
            elevator.raiseCommand(),
            elevator.releaseCommand(),
            drive.driveBackwardCommand().withTimeout(Seconds.of(2))
        ).named("Score And Back Up");
    }
}
```

**Why this order:** The class header (`b`) and brace (`f`), then the static method's signature (`h`) and brace (`j`). The method takes both mechanisms as parameters instead of reaching for global variables — dependency injection. `return Command.sequence(` (`d`) opens the sequence, and the order of its arguments *is* the order the robot does things: raise (`e`), then release (`i`), then back up (`a`). The last argument has no trailing comma, and `withTimeout(Seconds.of(2))` gives the drive step its 2-second end condition — `withTimeout` takes a `Time`, not a bare number. Unlike v2's `Commands.sequence(...)`, which returned a finished `Command`, `Command.sequence(...)` in v3 returns a builder, so the call ends with `.named("Score And Back Up")` (`g`) to turn it into a `Command` — leaving that off is a compile error. Then the method's brace (`c`) and the class's (`k`).
