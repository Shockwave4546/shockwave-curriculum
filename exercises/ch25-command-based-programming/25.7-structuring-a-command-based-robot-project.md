# Structuring a Command-Based Robot Project — Exercises

## Multiple Choice

**Question:** A new "hand-off" command has to move the `Elevator` down and run the `Wrist` at the same time, so a game piece can pass from one mechanism to the other. Neither subsystem is more "in charge" of the hand-off than the other, and the command has no internal state of its own. Which is the best way to define it so it can be reused from a button binding and from autonomous?

**Options:**

- A. A static factory method, like `HandoffCommands.handoff(elevator, wrist)`, that takes both subsystems as parameters
- B. An instance factory method on `Elevator`, like `elevator.handoffCommand()`
- C. A full `Command` subclass with its own fields for tracking state
- D. Make `elevator` and `wrist` `public static` fields in `RobotContainer`, so the command can reach them from anywhere

**Answer:** A

**Why:** A command that coordinates *multiple* subsystems doesn't naturally belong to any single one of them, which is exactly the case a static factory method is for. Passing both subsystems in as parameters is dependency injection: the method gets exactly what it needs, explicitly.

- B is wrong — an instance factory on one subsystem is best for a command tied to *that one* subsystem; here the `Elevator` would need to reach the `Wrist`, which it has no business owning.
- C is wrong — a full `Command` subclass is for a command with genuine internal state or unusually complex logic; this one has neither, so a whole class is unnecessary.
- D is wrong — making subsystems global lets any code anywhere call their methods directly, bypassing the scheduler's resource-management guarantees; subsystems stay `private` and get passed explicitly.

## Micro-Parsons

**Problem:** These lines, once correctly ordered, form a complete `AutoRoutines` class with one static factory method, `scoreAndBackUp`. It receives an `Elevator` and a `Drivetrain` as parameters, and returns a sequence that first raises the elevator, then releases the game piece, then drives backward for 2 seconds.

Reorder the fragments below into a working class:

- a. `            drivetrain.driveBackwardCommand().withTimeout(2.0)`
- b. `public class AutoRoutines`
- c. `    }`
- d. `        return Commands.sequence(`
- e. `            elevator.raiseCommand(),`
- f. `{`
- g. `        );`
- h. `    public static Command scoreAndBackUp(Elevator elevator, Drivetrain drivetrain)`
- i. `            elevator.releaseCommand(),`
- j. `    {`
- k. `}`

**Answer:** b, f, h, j, d, e, i, a, g, c, k

```java
public class AutoRoutines
{
    public static Command scoreAndBackUp(Elevator elevator, Drivetrain drivetrain)
    {
        return Commands.sequence(
            elevator.raiseCommand(),
            elevator.releaseCommand(),
            drivetrain.driveBackwardCommand().withTimeout(2.0)
        );
    }
}
```

**Why this order:** The class header (`b`) and brace (`f`), then the static method's signature (`h`) and brace (`j`). The method takes both subsystems as parameters instead of reaching for global variables — dependency injection. `return Commands.sequence(` (`d`) opens the sequence, and the order of its arguments *is* the order the robot does things: raise (`e`), then release (`i`), then back up (`a`). The last argument has no trailing comma, and `withTimeout(2.0)` gives the drive step its 2-second end condition. `);` (`g`) closes the call and ends the `return` statement, then the method's brace (`c`) and the class's (`k`).
