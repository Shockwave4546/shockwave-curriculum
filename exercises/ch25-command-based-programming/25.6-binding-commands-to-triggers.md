# Binding Commands to Triggers — Exercises

## Multiple Choice

**Question:** During setup, this binding is created:

```java
driverController.b().onTrue(Command.noRequirements(co -> gyro.reset()).named("Reset Gyro"));
```

The driver presses **B** and holds it down for 3 seconds before letting go. How many times does `gyro.reset()` run?

**Options:**

- A. Once, the instant B is first pressed
- B. About 150 times — once every 20ms loop while B is held
- C. Twice — once when B is pressed and once when it's released
- D. Zero times until B is released, then once

**Answer:** A

**Why:** `onTrue` schedules its command only on the change from false to true — the instant B goes down. Holding B keeps the trigger true, but there's no new false-to-true change, so nothing is scheduled again until B is released and pressed a second time. `Command.noRequirements(...)` builds a one-shot command that needs no mechanism (resetting a gyro doesn't control anything), and its body runs once, the same as any command whose body has no loop.

- B is wrong — scheduling every loop while held isn't what `onTrue` does; even `whileTrue` schedules its command once and keeps it running, rather than restarting it each loop.
- C is wrong — reacting to the release would need a separate `onFalse` binding; `onTrue` ignores the true-to-false change.
- D is wrong — that describes `onFalse`, which fires on the release; `onTrue` fires on the press.

## Micro-Parsons

**Problem:** These lines, once correctly ordered, form a complete class, `OperatorControls`, that creates an operator controller on port 1 and a `Climber` mechanism. Its constructor builds one trigger, `climbButtons`, that is true only while **both** bumpers are held, debounced by 0.25 seconds so a brief accidental touch doesn't count. It then binds `climber.climbCommand()` so the climber runs only while that trigger stays true.

Reorder the fragments below into a working class:

- a. `        climbButtons.whileTrue(climber.climbCommand());`
- b. `    public OperatorControls()`
- c. `}`
- d. `    private final CommandXboxController operator = new CommandXboxController(1);`
- e. `    {`
- f. `public class OperatorControls`
- g. `        Trigger climbButtons = operator.leftBumper().and(operator.rightBumper()).debounce(Seconds.of(0.25));`
- h. `    }`
- i. `{`
- j. `    private final Climber climber = new Climber();`

**Answer:** f, i, d, j, b, e, g, a, h, c

**Interchangeable:** (d, j)

```java
public class OperatorControls
{
    private final CommandXboxController operator = new CommandXboxController(1);
    private final Climber climber = new Climber();

    public OperatorControls()
    {
        Trigger climbButtons = operator.leftBumper().and(operator.rightBumper()).debounce(Seconds.of(0.25));
        climbButtons.whileTrue(climber.climbCommand());
    }
}
```

**Why this order:** The class header (`f`) and brace (`i`) come first, then the two fields (`d`, `j`) — the controller and the mechanism have to exist before the constructor can use them. The constructor (`b`, `e`) first builds the combined, debounced trigger (`g`) and stores it in `climbButtons`, and only then binds a command to it (`a`) — the variable can't be used before it's declared. `whileTrue` is the right binding here: it keeps `climbCommand()` running while both bumpers stay held and cancels it the instant either is released. `debounce` takes a `Time`, so the duration is `Seconds.of(0.25)`, not a bare `0.25`. The constructor's brace closes (`h`), then the class's (`c`).

`d` and `j` can go in either order: neither field's initializer uses the other, and both are created before the constructor body runs, whichever comes first.

## Coding

**Mode:** full-program

**Problem:** Commands v3 binds commands to buttons once, during setup, with `Trigger` methods. Bindings need a
real robot to run, so this exercise only checks that your code **compiles** and **uses the right
binding methods**: the fixed `main` reads your source file and reports whether a given call
appears in it (comments don't count).

Write `Wiring.configureButtons(controller, grab, release, eject)` so that:

- for the **right bumper**: `grab` runs once when it is **pressed** (`onTrue`) and `release` runs
  once when it is **released** (`onFalse`), chained on the same trigger;
- `eject` runs **only while** the **B** button is held (`whileTrue`), and stops the moment it is
  released.

For the input `onTrue`, the output is `onTrue: used` once your code calls `.onTrue(...)`, and
`onTrue: missing` until then. The other checks are `onFalse`, `whileTrue`, `rightBumper` and `b`.

```java
import java.nio.file.*;
import java.util.*;
import java.util.regex.*;
import org.wpilib.command3.Command;
import org.wpilib.command3.button.CommandXboxController;

public class Main
{
    // Don't change main
    public static void main(String[] args) throws Exception
    {
        // Compile-time check of the method's signature; this lambda is never run.
        Runnable signatureCheck = () -> Wiring.configureButtons(null, null, null, null);

        String source = Files.readString(Path.of("Main.java"))
            .replaceAll("(?s)/\\*.*?\\*/", "")
            .replaceAll("//.*", "");
        String call = new Scanner(System.in).next();
        boolean used = Pattern.compile("\\." + call + "\\s*\\(").matcher(source).find();
        System.out.println(call + ": " + (used ? "used" : "missing"));
    }
}

class Wiring
{
    public static void configureButtons(CommandXboxController controller, Command grab, Command release, Command eject)
    {
        controller.rightBumper()
            .onTrue(grab)
            .onFalse(release);
        controller.b().whileTrue(eject);
    }
}
```

**Why:** `rightBumper()` returns a `Trigger`, and every binding method returns the **same** trigger, so
`.onTrue(grab).onFalse(release)` chains both bindings onto the one trigger. `onTrue` fires once on
the press and `onFalse` once on the release. `whileTrue(eject)` is the right binding for "run while
held": it starts the command on the press and cancels it the moment the button is released, which
`onTrue` would not do. `toggleOnTrue` (a different method) would not count for `onTrue`, because the
check looks for the exact call `.onTrue(`. This is a structure check, not a behaviour test: it can
confirm the code compiles and uses these calls, but not that every command is the right one.
