# Binding Commands to Triggers — Exercises

## Multiple Choice

**Question:** During setup, this binding is created:

```java
driverController.b().onTrue(Command.noRequirements(co -> gyro.reset()).named("Reset Gyro"));
```

The driver presses **B** and holds it down for 3 seconds before letting go. How many times does `gyro.reset()` run?

**Options:**

- A. Once, the instant B is first pressed
- B. About 150 times — once every 20ms loop while B is held
- C. Twice — once when B is pressed and once when it's released
- D. Zero times until B is released, then once

**Answer:** A

**Why:** `onTrue` schedules its command only on the change from false to true — the instant B goes down. Holding B keeps the trigger true, but there's no new false-to-true change, so nothing is scheduled again until B is released and pressed a second time. `Command.noRequirements(...)` builds a one-shot command that needs no mechanism (resetting a gyro doesn't control anything), and its body runs once, the same as any command whose body has no loop.

- B is wrong — scheduling every loop while held isn't what `onTrue` does; even `whileTrue` schedules its command once and keeps it running, rather than restarting it each loop.
- C is wrong — reacting to the release would need a separate `onFalse` binding; `onTrue` ignores the true-to-false change.
- D is wrong — that describes `onFalse`, which fires on the release; `onTrue` fires on the press.

## Micro-Parsons

**Problem:** These lines, once correctly ordered, form a complete class, `OperatorControls`, that creates an operator controller on port 1 and a `Climber` mechanism. Its constructor builds one trigger, `climbButtons`, that is true only while **both** bumpers are held, debounced by 0.25 seconds so a brief accidental touch doesn't count. It then binds `climber.climbCommand()` so the climber runs only while that trigger stays true.

Reorder the fragments below into a working class:

- a. `        climbButtons.whileTrue(climber.climbCommand());`
- b. `    public OperatorControls()`
- c. `}`
- d. `    private final CommandXboxController operator = new CommandXboxController(1);`
- e. `    {`
- f. `public class OperatorControls`
- g. `        Trigger climbButtons = operator.leftBumper().and(operator.rightBumper()).debounce(Seconds.of(0.25));`
- h. `    }`
- i. `{`
- j. `    private final Climber climber = new Climber();`

**Answer:** f, i, d, j, b, e, g, a, h, c

**Interchangeable:** (d, j)

```java
public class OperatorControls
{
    private final CommandXboxController operator = new CommandXboxController(1);
    private final Climber climber = new Climber();

    public OperatorControls()
    {
        Trigger climbButtons = operator.leftBumper().and(operator.rightBumper()).debounce(Seconds.of(0.25));
        climbButtons.whileTrue(climber.climbCommand());
    }
}
```

**Why this order:** The class header (`f`) and brace (`i`) come first, then the two fields (`d`, `j`) — the controller and the mechanism have to exist before the constructor can use them. The constructor (`b`, `e`) first builds the combined, debounced trigger (`g`) and stores it in `climbButtons`, and only then binds a command to it (`a`) — the variable can't be used before it's declared. `whileTrue` is the right binding here: it keeps `climbCommand()` running while both bumpers stay held and cancels it the instant either is released. `debounce` takes a `Time`, so the duration is `Seconds.of(0.25)`, not a bare `0.25`. The constructor's brace closes (`h`), then the class's (`c`).

`d` and `j` can go in either order: neither field's initializer uses the other, and both are created before the constructor body runs, whichever comes first.

## Coding

**Mode:** full-program

**Problem:** Commands v3 binds commands to buttons once, during setup, with `Trigger` methods. Write
`Wiring.configureButtons(bumper, bButton, grab, release, eject)` so that:

- for the **bumper**: `grab` runs once when it is **pressed** (`onTrue`) and `release` runs once
  when it is **released** (`onFalse`), chained on the same trigger;
- `eject` runs **only while** the **B button** is held (`whileTrue`), every loop, and stops the
  moment it is released.

(On a real robot you would pass `driverController.rightBumper()` and `driverController.b()`; here the
fixed `main` makes two triggers from flags it flips.) The fixed `main` runs the **real scheduler**,
after one idle loop so each trigger records its starting state.
It reads a number of loops, then two numbers per loop (`bumper bButton`), where `1` means that button
is **held down** and `0` means it is released, and prints what ran in each loop. For the input
below:

```text
4
0 0
1 0
1 0
0 0
```

the output is:

```text
loop 1: []
loop 2: [grab start]
loop 3: []
loop 4: [release, grab end]
```

(The given `grab` command logs `grab start`, pauses for two loops, then logs `grab end`; `release` and
`eject` log their own names.)

**Starter:**

```java
import java.util.*;
import org.wpilib.command3.Command;
import org.wpilib.command3.Mechanism;
import org.wpilib.command3.Scheduler;
import org.wpilib.command3.TestSupport;
import org.wpilib.command3.Trigger;

public class Main
{
    private static final List<String> log = new ArrayList<>();

    // Don't change main
    public static void main(String[] args)
    {
        TestSupport.init(); // a fake robot clock and opmode, so the scheduler can run without a robot
        Scanner in = new Scanner(System.in);
        int loops = in.nextInt();

        Scheduler scheduler = Scheduler.getDefault();
        Hatch hatch = new Hatch();
        Latch latch = new Latch();
        Ejector ejector = new Ejector();
        Command grab = hatch.run(coroutine -> {
            log.add("grab start");
            coroutine.yield();
            coroutine.yield();
            log.add("grab end");
        }).named("Grab");
        Command release = latch.run(coroutine -> log.add("release")).named("Release");
        Command eject = ejector.runRepeatedly(() -> log.add("eject")).named("Eject");

        boolean[] held = new boolean[2]; // [0] = bumper, [1] = B button
        Trigger bumper = new Trigger(scheduler, () -> held[0]);
        Trigger bButton = new Trigger(scheduler, () -> held[1]);
        Wiring.configureButtons(bumper, bButton, grab, release, eject);

        scheduler.run(); // one idle loop first, so each trigger records its starting state
        log.clear();
        for (int i = 0; i < loops; i++)
        {
            held[0] = in.nextInt() == 1;
            held[1] = in.nextInt() == 1;
            log.clear();
            scheduler.run();
            System.out.println("loop " + (i + 1) + ": " + log);
        }
    }
}

class Hatch implements Mechanism
{
}

class Latch implements Mechanism
{
}

class Ejector implements Mechanism
{
}

class Wiring
{
    public static void configureButtons(Trigger bumper, Trigger bButton, Command grab, Command release, Command eject)
    {
        bumper
            .onTrue(grab)
            .onFalse(release);
        bButton.whileTrue(eject);
    }
}
```

**Why:** `bumper` is a `Trigger`, and every binding method returns the **same** trigger, so
`.onTrue(grab).onFalse(release)` chains both bindings onto the one trigger. `onTrue` fires **once**
on the press (loop 2), not again while the button is held (loop 3), and `onFalse` fires once on the
release (loop 4). `whileTrue(eject)` is the right binding for "run while held": the command starts
on the press, runs every loop the button stays down (an `onTrue` would run it only once), and is
canceled the moment the button is released. `toggleOnTrue` (a different method) would turn it on
and off with alternate presses instead: scenario 4 presses the bumper again while `grab` is still
running, and a toggle would cancel it there, so `grab end` would never print.
