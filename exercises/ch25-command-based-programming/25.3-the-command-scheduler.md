# The Command Scheduler — Exercises

## Multiple Choice

**Question:** An `Elevator` mechanism has a `currentHeight` field. During setup, this line registers a side job that copies the encoder's reading into `currentHeight`:

```java
Scheduler.getDefault().addPeriodic(() -> elevator.refreshHeight());
```

A running command's body reads `currentHeight`. Within a single call to `Scheduler.getDefault().run()`, which value does the command see?

**Options:**

- A. The height from the previous loop, because commands run before side jobs
- B. The height just refreshed in this same loop, because side jobs run before commands
- C. It changes from loop to loop, depending on whether the command or the side job was created first
- D. Always the height from when the robot turned on, because side jobs only run while no command is using the elevator

**Answer:** B

**Why:** Every scheduler loop runs in a fixed order, and side jobs added with `addPeriodic(...)` run early — before triggers are polled and before any command runs. By the time the command's body resumes (the last step), `currentHeight` has already been refreshed for this loop.

- A is wrong — it reverses the order: commands run *after* side jobs, not before.
- C is wrong — the order is the same every single loop, no matter which object was created first; that fixed order is exactly what makes command-based code predictable.
- D is wrong — a side job requires no mechanisms, so it runs every loop whether or not a command is using the elevator. (That's also why a side job should only update data, never drive the elevator's motor.)

## Micro-Parsons

**Problem:** A `Wrist` mechanism's default command, Hold Wrist, is currently running, and the scheduler also has one side job, which logs the wrist's angle. On this loop, a trigger's condition becomes true, and its `onTrue` binding schedules Tuck Wrist, which requires the wrist and has the default priority. Tuck Wrist's body calls `tuck()` once, with no loop — so it finishes the first time it runs.

These lines, once correctly ordered, form a complete program that prints — in order — what the scheduler does during this one loop.

Reorder the fragments below into a working program:

- a. `        System.out.println("Hold Wrist canceled");`
- b. `public class WristLoopTrace`
- c. `        System.out.println("Tuck Wrist finished");`
- d. `    }`
- e. `        System.out.println("Side job: log wrist angle");`
- f. `{`
- g. `        System.out.println("Tuck Wrist runs tuck()");`
- h. `    public static void main(String[] args)`
- i. `        System.out.println("Trigger queues Tuck Wrist");`
- j. `    {`
- k. `}`

**Answer:** b, f, h, j, e, i, a, g, c, d, k

```java
public class WristLoopTrace
{
    public static void main(String[] args)
    {
        System.out.println("Side job: log wrist angle");
        System.out.println("Trigger queues Tuck Wrist");
        System.out.println("Hold Wrist canceled");
        System.out.println("Tuck Wrist runs tuck()");
        System.out.println("Tuck Wrist finished");
    }
}
```

**Why this order:** After the usual class and `main` scaffolding (`b`, `f`, `h`, `j`), the trace follows the scheduler's fixed steps:

1. Side jobs run before anything else that matters here (`e`).
2. Polling triggers *queues* Tuck Wrist (`i`) — it doesn't start yet.
3. Queued commands are started. Tuck Wrist needs the wrist, which Hold Wrist has. Hold Wrist is a default command with the lowest priority, so Tuck Wrist wins: Hold Wrist is canceled right here (`a`), before Tuck Wrist ever runs.
4. Running commands take their turn: Tuck Wrist's body calls `tuck()` (`g`), reaches the end of its body, and is finished (`c`), freeing the wrist.

Hold Wrist doesn't restart during this loop: default commands are queued *before* queued commands start, and at that point Tuck Wrist was still queued for the wrist. On the next loop, the wrist is free, so Hold Wrist is queued and started again. Then `main`'s brace closes (`d`), then the class's (`k`).
