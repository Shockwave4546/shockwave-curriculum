# The Command Scheduler — Exercises

## Multiple Choice

**Question:** An `ElevatorSubsystem`'s `periodic()` method updates a `currentHeight` field from the encoder. A running command's `execute()` reads `currentHeight`. Within a single call to `CommandScheduler.getInstance().run()`, which value does `execute()` see?

**Options:**

- A. The height from the previous loop, because commands run before subsystems update
- B. The height just updated in this same loop, because subsystem `periodic()` methods run before commands execute
- C. It changes from loop to loop, depending on whether the command or the subsystem was created first
- D. Always 0, because `periodic()` only runs when no command is using the subsystem

**Answer:** B

**Why:** Every scheduler iteration runs in a fixed order, and step 1 is every registered subsystem's `periodic()`. By the time commands run (step 3), `currentHeight` has already been refreshed for this loop.

- A is wrong — it reverses the order: commands run *after* subsystem `periodic()` methods, not before.
- C is wrong — the order is the same every single loop, no matter which object was created first; that fixed order is exactly what makes command-based code predictable.
- D is wrong — a subsystem's `periodic()` runs every loop whether or not a command is currently using that subsystem.

## Micro-Parsons

**Problem:** A `WristSubsystem` has a default command, `HoldWrist`, which is currently running. On this loop, a trigger's condition becomes true and schedules `TuckWrist`, which also requires the wrist. Both commands use the default interruption behavior, and `TuckWrist.isFinished()` returns `true` the first time it's checked.

These lines, once correctly ordered, form a complete program that prints — in order — every call the scheduler makes during this one loop.

Reorder the fragments below into a working program:

- a. `        System.out.println("TuckWrist.initialize()");`
- b. `public class WristLoopTrace`
- c. `        System.out.println("HoldWrist.initialize()");`
- d. `    }`
- e. `        System.out.println("wrist.periodic()");`
- f. `{`
- g. `        System.out.println("TuckWrist.end(false)");`
- h. `    public static void main(String[] args)`
- i. `        System.out.println("HoldWrist.end(true)");`
- j. `    {`
- k. `        System.out.println("TuckWrist.execute()");`
- l. `}`

**Answer:** b, f, h, j, e, i, a, k, g, c, d, l

```java
public class WristLoopTrace
{
    public static void main(String[] args)
    {
        System.out.println("wrist.periodic()");
        System.out.println("HoldWrist.end(true)");
        System.out.println("TuckWrist.initialize()");
        System.out.println("TuckWrist.execute()");
        System.out.println("TuckWrist.end(false)");
        System.out.println("HoldWrist.initialize()");
    }
}
```

**Why this order:** After the usual class and `main` scaffolding (`b`, `f`, `h`, `j`), the trace follows the scheduler's fixed steps:

1. Subsystem `periodic()` methods always run first (`e`).
2. Polling triggers schedules `TuckWrist`. It needs the wrist, which `HoldWrist` already has — and under the default interruption behavior, the running command is the one that gets canceled, so `HoldWrist.end(true)` (`i`) runs *before* `TuckWrist` takes over with `initialize()` (`a`). `true` means `HoldWrist` was interrupted, not finished.
3. Scheduled commands run: `TuckWrist.execute()` (`k`), then its `isFinished()` returns `true`, so `TuckWrist.end(false)` (`g`) runs — `false`, because it finished on its own — and the wrist is freed.
4. The wrist is free and has a default command, so `HoldWrist` is scheduled again, and its `initialize()` (`c`) runs.

`HoldWrist` never gets an `execute()` this loop: it was canceled before step 3 and only rescheduled in step 4, so its next `execute()` is on the following loop. Then `main`'s brace closes (`d`), then the class's (`l`).
