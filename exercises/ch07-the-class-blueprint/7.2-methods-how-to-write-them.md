# Methods: How to Write Them — Exercises

## Multiple Choice

**Question:** A `Transmission` class has a private instance variable `private int currentGear;`. A teammate writes this method, intending it as a getter:

```java
public void getCurrentGear()
{
    System.out.println(currentGear);
}
```

Other code then tries `int gear = myTransmission.getCurrentGear();`, and it fails to compile. What's wrong with the method?

**Options:**

- A. It's `void`, so it doesn't return a value at all — a getter must be non-`void` and `return` the instance variable, not just print it
- B. It's missing the `private` keyword, so other classes can't call it
- C. `currentGear` needs to be `public` before any method can read it
- D. Getter methods must take one parameter — the value being returned

**Answer:** A

**Why:** A getter's whole job is to hand a value back to whoever called it, which requires a return type matching the field and a `return` statement. This method is `void` and only prints — it never hands anything back, so `int gear = myTransmission.getCurrentGear();` has nothing to assign to `gear`, and that's a compile error.

- B is wrong — the method is already declared `public`, exactly as a getter should be; that's not the problem here.
- C is wrong — getters exist precisely so an instance variable *can* stay `private` while still being readable from outside; making `currentGear` `public` would remove the need for this getter, not fix it.
- D is wrong — getters conventionally take zero parameters; adding one would make this a different kind of method entirely, not fix the missing return value.

## Micro-Parsons

**Problem:** This lesson emphasizes getters *and* setters as a pair, so scrambling only a getter would tell half the story — but a full getter+setter+`main` program runs well past a reasonable fragment count. Below is the outer scaffold of a complete program: the `Elevator` class declaration and its `main` method signature, with their opening and closing braces already fixed in place. Reorder the fragments below to fill in the two blanks: the class's field plus its getter and setter methods (blank 1), and the three statements inside `main` that construct an `Elevator`, raise it to a new height, and print that height back out (blank 2).

```java
public class Elevator
{
    // ⟵ blank 1: field, getter, setter

    public static void main(String[] args)
    {
        // ⟵ blank 2: three statements
    }
}
```

Reorder the fragments below to fill both blanks:

- a. `        return heightInches;`
- b. `    public double getHeightInches()`
- c. `        Elevator e = new Elevator();`
- d. `    private double heightInches;`
- e. `    {`
- f. `        heightInches = newHeight;`
- g. `    {`
- h. `    }`
- i. `    public void setHeightInches(double newHeight)`
- j. `        e.setHeightInches(24.0);`
- k. `    }`
- l. `        System.out.println(e.getHeightInches());`

**Answer:**
- Blank 1 (class body): d, b, e, a, h, i, g, f, k
- Blank 2 (`main` body): c, j, l

```java
public class Elevator
{
    private double heightInches;

    public double getHeightInches()
    {
        return heightInches;
    }

    public void setHeightInches(double newHeight)
    {
        heightInches = newHeight;
    }

    public static void main(String[] args)
    {
        Elevator e = new Elevator();
        e.setHeightInches(24.0);
        System.out.println(e.getHeightInches());
    }
}
```

**Why this order:** With the class declaration, `main`'s signature, and all four of their braces held fixed as scaffold, only the substantive fragments are left to place. In blank 1, the field (`d`) is declared first, then the getter (`b`, `e`, `a`, `h` — signature, opening brace, `return` statement, closing brace), followed by the setter (`i`, `g`, `f`, `k`) in that same signature/brace/statement/brace shape, matching this lesson's getter-then-setter presentation. In blank 2, the three statements only make sense in one order: `c` constructs an `Elevator` (there has to be an object before anything can be called on it), `j` calls the setter on it to establish a real height, and `l` calls the getter to print that height back — showing the getter and setter working together rather than just one in isolation. Note that `e` and `g` (both a bare four-space `{`) are textually identical, as are `h` and `k` (both a bare four-space `}`) — one pair belongs to the getter and the other to the setter, so it doesn't matter which physical copy lands in which slot as long as each method gets one opening and one closing brace.
