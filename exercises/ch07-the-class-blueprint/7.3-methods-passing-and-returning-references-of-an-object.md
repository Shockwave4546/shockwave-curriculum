# Methods: Passing & Returning References of an Object — Exercises

## Multiple Choice

**Question:** A `Locker` class has a private, mutable instance variable `combination` (type `Combination`, which has a `setCode` method), and this getter:

```java
public Combination getCombination()
{
    return combination;
}
```

Code elsewhere does:

```java
Combination c = myLocker.getCombination();
c.setCode(1234);
```

What happens to `myLocker`'s actual stored combination?

**Options:**

- A. It also changes to code `1234` — the getter returned a reference to the real `Combination` object, not a separate copy, so `c` and `myLocker`'s internal combination are the same object
- B. Nothing changes — `getCombination()` always hands back a brand-new copy automatically
- C. It only changes the next time `myLocker`'s constructor is called
- D. It's a compile error — you can't call a setter on a value returned from a getter

**Answer:** A

**Why:** Java is always call by value, but for an object, the value copied is the reference. Returning `combination` directly hands the caller the *real* object, not a copy — so `c` and `myLocker`'s internal `combination` point at the exact same `Combination`, and calling `c.setCode(1234)` changes the one object both of them see.

- B is wrong — Java never makes a defensive copy automatically; that has to be written explicitly (e.g. `new Combination(...)`), which this getter doesn't do.
- C is wrong — constructing `myLocker` again has nothing to do with it; the change takes effect the instant `setCode` runs.
- D is wrong — this compiles fine. `c` has type `Combination`, and `Combination` has a `setCode` method, so the call is valid.

## Micro-Parsons

**Problem:** `Combination` (defined elsewhere) has a constructor `Combination(int initCode)` and a method `getCode()`. These lines, once correctly ordered, form a complete program whose `Locker` class has a constructor that stores a defensive copy of the `Combination` it's given, instead of the original reference, then builds one `Locker` from a fresh `Combination`.

Reorder the fragments below into a working program:

- a. `        combination = new Combination(initCombination.getCode());`
- b. `public class Locker`
- c. `    }`
- d. `    private Combination combination;`
- e. `    public Locker(Combination initCombination)`
- f. `{`
- g. `    {`
- h. `}`
- i. `    public static void main(String[] args)`
- j. `    {`
- k. `        Locker locker = new Locker(new Combination(1234));`
- l. `    }`

**Answer:** b, f, d, e, g, a, c, i, j, k, l, h

```java
public class Locker
{
    private Combination combination;

    public Locker(Combination initCombination)
    {
        combination = new Combination(initCombination.getCode());
    }

    public static void main(String[] args)
    {
        Locker locker = new Locker(new Combination(1234));
    }
}
```

**Why this order:** The class declaration (`b`) and its opening brace (`f`) come first, followed by the instance variable (`d`) — declared before the constructor, per the usual order. The constructor's signature (`e`) and its own opening brace (`g`) come next. Inside, the key line (`a`) builds a *brand-new* `Combination` from the passed-in one's own code (`initCombination.getCode()`), rather than storing `initCombination` itself — that's the defensive copy. The constructor's body then closes (`c`), and `main` (`i`) is declared next with its own opening brace (`j`); inside it, the single statement (`k`) builds a `Combination` and immediately hands it to a new `Locker`, exercising the defensive-copy constructor. Finally, the braces close in reverse: `main`'s body (`l`), then the class's body (`h`). Note that `g`/`j` (both a bare four-space `{`) and `c`/`l` (both a bare four-space `}`) are textually identical — interchangeable copies at the same nesting depth, one pair per block, so it doesn't matter which physical copy lands in which slot as long as one opens the constructor and one opens `main`.
