# Methods: Passing & Returning References of an Object — Exercises

## Multiple Choice

**Question:** A `Locker` class has a private, mutable instance variable `combination` (type `Combination`, which has a `setCode` method), and this getter:

```java
public Combination getCombination()
{
    return combination;
}
```

Code elsewhere does:

```java
Combination c = myLocker.getCombination();
c.setCode(1234);
```

What happens to `myLocker`'s actual stored combination?

**Options:**

- A. It also changes to code `1234` — the getter returned a reference to the real `Combination` object, not a separate copy, so `c` and `myLocker`'s internal combination are the same object
- B. Nothing changes — `getCombination()` always hands back a brand-new copy automatically
- C. It only changes the next time `myLocker`'s constructor is called
- D. It's a compile error — you can't call a setter on a value returned from a getter

**Answer:** A

**Why:** Java is always call by value, but for an object, the value copied is the reference. Returning `combination` directly hands the caller the *real* object, not a copy — so `c` and `myLocker`'s internal `combination` point at the exact same `Combination`, and calling `c.setCode(1234)` changes the one object both of them see.

- B is wrong — Java never makes a defensive copy automatically; that has to be written explicitly (e.g. `new Combination(...)`), which this getter doesn't do.
- C is wrong — constructing `myLocker` again has nothing to do with it; the change takes effect the instant `setCode` runs.
- D is wrong — this compiles fine. `c` has type `Combination`, and `Combination` has a `setCode` method, so the call is valid.

## Micro-Parsons

**Problem:** `Combination` is a fixed, already-complete class shown below — assume it exists exactly as written and don't reorder it. It has a constructor `Combination(int initCode)` and a method `getCode()`. It goes *after* your `Locker` class in the file (the `public` class with `main` comes first, per this course's file-ordering rule — Lesson 7.3's box below). Reorder only the fragments below into the `Locker` class, whose constructor stores a defensive copy of the `Combination` it's given, instead of the original reference, then builds one `Locker` from a fresh `Combination`.

```java
class Combination
{
    private int code;

    public Combination(int initCode)
    {
        code = initCode;
    }

    public int getCode()
    {
        return code;
    }
}
```

Reorder the fragments below into the `Locker` class that comes *before* it:

- a. `        combination = new Combination(initCombination.getCode());`
- b. `public class Locker`
- c. `    }`
- d. `    private Combination combination;`
- e. `    public Locker(Combination initCombination)`
- f. `{`
- g. `    {`
- h. `}`
- i. `    public static void main(String[] args)`
- j. `    {`
- k. `        Locker locker = new Locker(new Combination(1234));`
- l. `    }`

**Answer:** b, f, d, e, g, a, c, i, j, k, l, h

**Interchangeable:** (g, j) (c, l)

```java
public class Locker
{
    private Combination combination;

    public Locker(Combination initCombination)
    {
        combination = new Combination(initCombination.getCode());
    }

    public static void main(String[] args)
    {
        Locker locker = new Locker(new Combination(1234));
    }
}

class Combination
{
    private int code;

    public Combination(int initCode)
    {
        code = initCode;
    }

    public int getCode()
    {
        return code;
    }
}
```

**Why this order:** The class declaration (`b`) and its opening brace (`f`) come first, followed by the instance variable (`d`) — declared before the constructor, per the usual order. The constructor's signature (`e`) and its own opening brace (`g`) come next. Inside, the key line (`a`) builds a *brand-new* `Combination` from the passed-in one's own code (`initCombination.getCode()`), rather than storing `initCombination` itself — that's the defensive copy. The constructor's body then closes (`c`), and `main` (`i`) is declared next with its own opening brace (`j`); inside it, the single statement (`k`) builds a `Combination` and immediately hands it to a new `Locker`, exercising the defensive-copy constructor. Finally, the braces close in reverse: `main`'s body (`l`), then the class's body (`h`) — `Locker` is `public` and holds `main`, so it has to come first in the file (Lesson 7.3); the given `Combination` class follows it. Note that `g`/`j` (both a bare four-space `{`) and `c`/`l` (both a bare four-space `}`) are textually identical — interchangeable copies at the same nesting depth, one pair per block, so it doesn't matter which physical copy lands in which slot as long as one opens the constructor and one opens `main`.

## Coding

**Mode:** full-program

**Problem:** A `Subsystem` **has a** `MotorConfig` (current limit and ramp rate). `MotorConfig` is given below and
it is mutable: it has a setter for the current limit. Finish `Subsystem` so that outside code can never
change the subsystem's settings by accident:

- The constructor must keep its **own copy** of the `MotorConfig` it is handed (a defensive copy), not the
  caller's object.
- `getConfig()` must return a **copy** too, not the real object.

The fixed `main` builds a config, gives it to a subsystem, then changes the *original* config's limit and
prints the subsystem's limit. Then it fetches the config with `getConfig()`, changes *that* one to `0`, and
prints the subsystem's limit again. Both prints must still show the limit the subsystem was built with.

For example, the input `Intake 40 0.25 60` (name, limit, ramp rate, a new limit to try) prints `40 A`
both times; the first line also shows the ramp rate `0.25`.

**Starter:**

```java
import java.util.*;

public class Main
{
    // Don't change main
    public static void main(String[] args)
    {
        Scanner in = new Scanner(System.in);
        String name = in.next();
        int limit = in.nextInt();
        double ramp = in.nextDouble();
        int newLimit = in.nextInt();

        MotorConfig original = new MotorConfig(limit, ramp);
        Subsystem subsystem = new Subsystem(name, original);

        original.setCurrentLimit(newLimit);
        System.out.println(subsystem.getName() + " after changing the original: "
            + subsystem.getConfig().getCurrentLimit() + " A, ramp " + subsystem.getConfig().getRampRate());

        MotorConfig fetched = subsystem.getConfig();
        fetched.setCurrentLimit(0);
        System.out.println(subsystem.getName() + " after changing the fetched one: "
            + subsystem.getConfig().getCurrentLimit() + " A");
    }
}

// Given: a mutable settings class (it has setters)
class MotorConfig
{
    private int currentLimit;
    private double rampRate;

    public MotorConfig(int initCurrentLimit, double initRampRate)
    {
        currentLimit = initCurrentLimit;
        rampRate = initRampRate;
    }

    public int getCurrentLimit()
    {
        return currentLimit;
    }

    public double getRampRate()
    {
        return rampRate;
    }

    public void setCurrentLimit(int newCurrentLimit)
    {
        currentLimit = newCurrentLimit;
    }
}

class Subsystem
{
    private String name;
    private MotorConfig config;

    public Subsystem(String initName, MotorConfig initConfig)
    {
        // TODO: store the name, and keep your OWN copy of the config
    }

    public String getName()
    {
        return name;
    }

    public MotorConfig getConfig()
    {
        // TODO: hand back a copy, not the real object
        return null;
    }
}
```

**Solution:**

```java
import java.util.*;

public class Main
{
    // Don't change main
    public static void main(String[] args)
    {
        Scanner in = new Scanner(System.in);
        String name = in.next();
        int limit = in.nextInt();
        double ramp = in.nextDouble();
        int newLimit = in.nextInt();

        MotorConfig original = new MotorConfig(limit, ramp);
        Subsystem subsystem = new Subsystem(name, original);

        original.setCurrentLimit(newLimit);
        System.out.println(subsystem.getName() + " after changing the original: "
            + subsystem.getConfig().getCurrentLimit() + " A, ramp " + subsystem.getConfig().getRampRate());

        MotorConfig fetched = subsystem.getConfig();
        fetched.setCurrentLimit(0);
        System.out.println(subsystem.getName() + " after changing the fetched one: "
            + subsystem.getConfig().getCurrentLimit() + " A");
    }
}

// Given: a mutable settings class (it has setters)
class MotorConfig
{
    private int currentLimit;
    private double rampRate;

    public MotorConfig(int initCurrentLimit, double initRampRate)
    {
        currentLimit = initCurrentLimit;
        rampRate = initRampRate;
    }

    public int getCurrentLimit()
    {
        return currentLimit;
    }

    public double getRampRate()
    {
        return rampRate;
    }

    public void setCurrentLimit(int newCurrentLimit)
    {
        currentLimit = newCurrentLimit;
    }
}

class Subsystem
{
    private String name;
    private MotorConfig config;

    public Subsystem(String initName, MotorConfig initConfig)
    {
        name = initName;
        config = new MotorConfig(initConfig.getCurrentLimit(), initConfig.getRampRate());
    }

    public String getName()
    {
        return name;
    }

    public MotorConfig getConfig()
    {
        return new MotorConfig(config.getCurrentLimit(), config.getRampRate());
    }
}
```

**Why:** Passing an object copies its reference, so `config = initConfig;` would leave `main`'s `original` and
the subsystem's `config` pointing at the same object, and the first print would show the new limit
(`60 A`). Building a `new MotorConfig(...)` from the getters' values gives the subsystem an object nobody
else holds. The same rule runs backward: returning `config` directly would let `main` call
`setCurrentLimit(0)` on the subsystem's real settings, so the second print would show `0 A`. Returning a
copy closes that door. `name` needs no copy because `String` is immutable.
