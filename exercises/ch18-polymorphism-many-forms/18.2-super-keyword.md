# super Keyword — Exercises

## Multiple Choice

**Question:** Given these two classes:

```java
class Hood
{
    public void aim()
    {
        System.out.println("Hood: set angle");
    }
}

class AutoHood extends Hood
{
    @Override
    public void aim()
    {
        System.out.println("AutoHood: read distance");
        super.aim();
        System.out.println("AutoHood: angle locked");
    }
}
```

What does `new AutoHood().aim();` print?

**Options:**

- A. `Hood: set angle`, then `AutoHood: read distance`, then `AutoHood: angle locked`
- B. `AutoHood: read distance`, then `AutoHood: angle locked`
- C. Nothing — it doesn't compile, because `super.aim()` must be the first statement in the method
- D. `AutoHood: read distance`, then `Hood: set angle`, then `AutoHood: angle locked`

**Answer:** D

**Why:** The object is an `AutoHood`, so `AutoHood`'s override runs. Its statements run top to bottom: first its own `println`, then `super.aim()` — which runs `Hood`'s version, printing `Hood: set angle` — and then, once that returns, the override's last `println`.

- A is wrong — `super.aim()` doesn't jump to the front of the method. It's an ordinary call that runs exactly where it's written, which here is the second statement.
- B is wrong — that would be the output if the override *didn't* call `super.aim()`. Because it does, `Hood`'s version runs too.
- C is wrong — it confuses the two forms of `super`. Only `super(...)`, the constructor call, has placement rules: on Java 17 it must be a constructor's first statement, and on Java 25 only statements that don't use the object may come before it. `super.aim()` calls a method and can appear anywhere in a method body.

## Micro-Parsons

**Problem:** Given this `Conveyor` class and `main` method, reorder the fragments below into the `IndexingConveyor` class that goes where the comment is. `IndexingConveyor` must extend `Conveyor` and override `run()` so that it reuses `Conveyor`'s version *and then* adds its own line. The program should print:

```
Conveyor: belt moving
IndexingConveyor: game piece staged
```

```java
public class ConveyorTest
{
    public static void main(String[] args)
    {
        IndexingConveyor indexer = new IndexingConveyor();
        indexer.run();
    }
}

class Conveyor
{
    public void run()
    {
        System.out.println("Conveyor: belt moving");
    }
}

// IndexingConveyor class goes here
```

Reorder the fragments below to complete it:

- a. `        super.run();`
- b. `    {`
- c. `}`
- d. `    @Override`
- e. `        System.out.println("IndexingConveyor: game piece staged");`
- f. `class IndexingConveyor extends Conveyor`
- g. `    }`
- h. `    public void run()`
- i. `{`

**Answer:** f, i, d, h, b, a, e, g, c

```java
public class ConveyorTest
{
    public static void main(String[] args)
    {
        IndexingConveyor indexer = new IndexingConveyor();
        indexer.run();
    }
}

class Conveyor
{
    public void run()
    {
        System.out.println("Conveyor: belt moving");
    }
}

class IndexingConveyor extends Conveyor
{
    @Override
    public void run()
    {
        super.run();
        System.out.println("IndexingConveyor: game piece staged");
    }
}
```

**Why this order:** The class declaration (`f`) and its opening brace (`i`) come first. `@Override` (`d`) sits directly above the method signature (`h`), followed by the method's opening brace (`b`). Inside the body, `super.run()` (`a`) must come *before* the `println` (`e`): `super.run()` is an ordinary method call that runs exactly where it's placed, so putting it first is what makes `Conveyor: belt moving` print before `IndexingConveyor: game piece staged`. Swapping `a` and `e` would still compile, but the two lines would print in the wrong order. The method's closing brace (`g`) and the class's closing brace (`c`) finish it. The `Conveyor` class and `ConveyorTest`'s `main` are the given scaffold.


## Coding

**Mode:** full-program

**Problem:** `RobotPart` (below, already written, and not to be changed) has a `stop()` that logs
`stopped` and a `toString()` that returns the part's name. Write two subclasses that **extend**
those inherited behaviors with `super`, instead of replacing them:

- `Climber`, constructor `Climber(String name)`. Its `stop()` override must **first** do everything
  `RobotPart`'s `stop()` does, **then** log `brake engaged`.
- `Intake`, constructor `Intake(String name, boolean hasGamePiece)`. Its `toString()` override
  returns whatever `RobotPart`'s `toString()` returns, followed by ` (hasGamePiece=` and the
  boolean and `)`. Build it from the superclass's version rather than from scratch.

The fixed `main` reads a count, then one line per part, either `climber name` (stop it) or
`intake name true/false` (print it). For the input `2 climber Left intake Front true`:

```text
[Left] stopped
[Left] brake engaged
Front (hasGamePiece=true)
```

**Starter:**


**Solution:**

```java
import java.util.*;

public class Main
{
    // Don't change main
    public static void main(String[] args)
    {
        Scanner in = new Scanner(System.in);
        int count = in.nextInt();
        for (int i = 0; i < count; i++)
        {
            String kind = in.next();
            String name = in.next();
            if (kind.equals("climber"))
            {
                new Climber(name).stop();
            }
            else
            {
                System.out.println(new Intake(name, in.nextBoolean()));
            }
        }
    }
}

// Don't change RobotPart
class RobotPart
{
    private String name;

    public RobotPart(String name) { this.name = name; }
    public String getName() { return name; }
    public void log(String msg) { System.out.println("[" + name + "] " + msg); }
    public void stop() { log("stopped"); }

    @Override
    public String toString() { return name; }
}

class Climber extends RobotPart
{
    public Climber(String name) { super(name); }

    @Override
    public void stop()
    {
        super.stop();
        log("brake engaged");
    }
}

class Intake extends RobotPart
{
    private boolean hasGamePiece;

    public Intake(String name, boolean hasGamePiece)
    {
        super(name);
        this.hasGamePiece = hasGamePiece;
    }

    @Override
    public String toString()
    {
        return super.toString() + " (hasGamePiece=" + hasGamePiece + ")";
    }
}
```

**Why:** An override throws away the inherited version unless it calls `super.method()` itself, and
that call is never automatic, unlike the implicit `super()` in a constructor. `Climber.stop()` calls
`super.stop()` first, so the `stopped` line prints before `brake engaged`. A version that only
writes `log("brake engaged")` replaces the inherited behavior and loses the first line. `Intake`
uses the same idea on `toString()`: `super.toString()` supplies the name, and the override adds to
it, so it keeps working even if `RobotPart`'s `toString()` later changes.
